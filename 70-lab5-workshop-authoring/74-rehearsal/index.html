    5-4. 리허설 (선택)¶

    워크숍 페이지는 한 번 끝까지 실제로 돌려 봐야 완성됩니다. lint와 정책 검사는 형식만 봅니다. 서비스 순서 제약, 실제 소요 시간, 실제 출력은 배포해 봐야 압니다. 이 페이지는 리허설을 AI와 함께 하는 방법과, 오늘 실습에서 배포하지 않는 경우의 대안을 설명합니다.

    Warning

    오늘 실습에서 배포는 선택입니다. Cloud WAN core network edge는 edge 하나에 시간당 USD 0.50이고(이 모듈은 edge 2개), TGW peering 연결에도 리전별 시간당 요금이 붙습니다. TGW와 VPC attachment 요금도 별도입니다. 요금: AWS Cloud WAN, AWS Transit Gateway. core network 생성과 policy 적용에는 시간이 걸립니다. 남은 실습 시간이 30분 미만이면 배포하지 말고 아래 "배포하지 않는 경우"로 진행하세요.

    배포하지 않는 경우: 리허설 계획 만들기¶

    Claude Code에 입력:

    scripts/validate.sh를 실행하고 결과를 보여 줘.
그다음 이 모듈의 리허설 체크리스트를 docs/rehearsal-checklist.md로 만들어 줘:
- 배포 순서와 스택 이름, 각 단계에서 기록할 값(소요 시간, 명령 출력)
- 리허설에서만 확인할 수 있는 열린 질문 (storyboard.md의 열린 질문 포함)
- 삭제 순서와 삭제 후 남은 리소스 확인 명령

    Info

    Tip: 사람만 하는 단계는 wizard로. Workshop Studio 이벤트 만들기, 참석자 계정의 Bedrock 모델 접근 확인처럼 콘솔에서 사람이 해야 하는 준비 단계는 wizard skill로 대화형 bash 안내 스크립트를 만들어 두면, 다음 행사 때 같은 순서로 빠짐없이 할 수 있습니다. 예: "이벤트 준비 절차를 wizard로 만들어 줘". 설명: 1-6. Matt Pocock skills

    배포하는 경우: 단계별 리허설¶

    리허설은 강사 계정이나 별도 테스트 계정에서 합니다. 각 단계 뒤에 증적을 남기도록 지시합니다.

    Claude Code에 입력:

    리허설을 하자. scripts/deploy.sh before를 실행하고 끝나면 scripts/show-routes.sh 출력을 results/00-before.txt에 저장해 줘.
단계마다 시작·종료 시각을 results/timing.md에 기록해 줘. 오류가 나면 고치기 전에 원인 가설과 근거(스택 이벤트)를 먼저 보여 줘.
    순서 명령 만드는 스택 (리전) 확인
    1 deploy.sh before ws-ai-nssa-cwan-base-sel (서울), ws-ai-nssa-cwan-base-tyo (도쿄), ws-ai-nssa-cwan-peering (서울), ws-ai-nssa-cwan-routes-sel / -routes-tyo prod RT에 원격 prod CIDR이 static
    2 deploy.sh after ws-ai-nssa-cwan-core (서울), ws-ai-nssa-cwan-attach-sel / -attach-tyo attachment 4개 AVAILABLE, 세그먼트 prod/dev
    3 deploy.sh precheck 바꾸는 것 없음 attachment 4개 AVAILABLE, 각 edge의 Cloud WAN 세그먼트 경로표에 상대 리전 CIDR이 있음(get-network-routes)
    4 deploy.sh cutover precheck를 다시 돌려 통과할 때만 routes-*, peering 스택 삭제 원격 CIDR이 propagated로 바뀜, dev RT에 prod CIDR 없음

    스크립트는 5-2 4단계에서 ~/ws-solutions/cloudwan/scripts/로부터 scripts/에 복사해 두었습니다. 모든 스택은 --tags Project=ws-ai-nssa로 배포되므로 정리의 태그 조회에도 잡힙니다.

    deploy.sh는 병렬로 띄운 배포를 PID마다 기다려 하나라도 실패하면 멈춥니다. cut-over는 기존 경로를 지우는 되돌리기 어려운 작업이라, Cloud WAN이 상대 리전 경로를 이미 갖고 있는지 확인(precheck)한 뒤에만 진행합니다. deploy.sh는 TGW peering 수락(도쿄)처럼 CloudFormation 밖에서 해야 하는 일도 포함합니다. aws ec2 wait에는 TGW attachment용 waiter가 없어서 상태를 직접 폴링합니다. AI가 없는 waiter(transit-gateway-attachment-available 등)를 쓰는 경우가 많으니 aws ec2 wait help로 확인하세요.

    Info

    리허설에서 확인할 열린 질문

    • ws-ai-nssa-cwan-core 스택을 서울에 배포해도 되는지(Network Manager는 홈 리전 API를 씁니다), core network가 AVAILABLE이 되기까지 실제 몇 분인지.
    • 40-cwan-tgw-peering.yaml의 policy table association이 꼭 필요한지, 순서(peering AVAILABLE → attachment)가 DependsOn만으로 지켜지는지.
    • cut-over 중 경로가 바뀌는 순간의 영향(EC2 ping 선택 과제로 측정).

    확인한 결과는 AGENTS.md와 페이지의 "예상 출력"에 반영하고 <!-- 리허설 전 --> 주석을 지웁니다.

    정리 (배포한 경우 꼭 실행)¶

    삭제는 만든 순서의 역순입니다. attachment가 남아 있으면 core network를 지울 수 없고, peering이 남아 있으면 TGW를 지울 수 없습니다.

    순서 삭제할 스택 리전
    1 ws-ai-nssa-cwan-attach-sel, ws-ai-nssa-cwan-attach-tyo 서울, 도쿄
    2 ws-ai-nssa-cwan-core 서울
    3 ws-ai-nssa-cwan-routes-sel, ws-ai-nssa-cwan-routes-tyo (cut-over 했다면 이미 없음) 서울, 도쿄
    4 ws-ai-nssa-cwan-peering (cut-over 했다면 이미 없음) 서울
    5 ws-ai-nssa-cwan-base-sel, ws-ai-nssa-cwan-base-tyo 서울, 도쿄

    Claude Code에 입력:

    scripts/cleanup.sh로 이 모듈의 스택을 모두 지워 줘. 실행 전에 지울 스택 목록과 리전을 먼저 보여 주고 내 확인을 받아.
끝나면 두 리전에 ws-ai-nssa-cwan- 스택과 Network Manager global network가 남았는지 확인해 줘.

    남은 global network는 다음 명령으로 확인합니다.

    aws networkmanager describe-global-networks --region us-west-2 \
  --query 'GlobalNetworks[].[GlobalNetworkId,State,Tags[?Key==`Name`]|[0].Value]' --output table
