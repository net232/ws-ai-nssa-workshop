    5-2. 토폴로지를 IaC로¶

    이 단계에서는 core network policy JSON과 검사기를 Claude와 직접 만들고, CloudFormation 템플릿은 정답을 복사해 검토합니다. Cloud WAN policy는 AI가 그럴듯하지만 없는 키를 만들기 쉬운 대표적인 문서입니다. 키 이름이 사람이 읽기 좋은 영어 단어(isolate, segment-name …)라서, 기억에 기대어 쓰면 틀려도 티가 나지 않습니다. 그래서 이 페이지의 절반은 검증입니다.

    1단계. core network policy 만들기¶

    Claude Code에 입력:

    storyboard.md 모듈 1~2에 쓸 Cloud WAN core network policy를 policy/core-network-policy.json으로 만들어 줘.

- version 2021.12, edge-locations: ap-northeast-2, ap-northeast-1
- asn-ranges 64512-64520 (TGW ASN 64600, 64601과 겹치면 안 됨)
- 세그먼트 prod, dev. 서로 share하지 않음. 워크숍이므로 attachment 승인은 자동
- attachment-policies: TGW route table attachment 중 태그 segment=prod는 prod, segment=dev는 dev

먼저 AWS 문서의 "Core network policy version parameters" 페이지를 찾아 읽고, 쓴 키마다 문서에서 확인했는지 표로 보여 줘.

    Claude가 MCP(aws-knowledge)로 문서를 찾는지 화면에서 확인하세요. 도구 호출 없이 바로 JSON을 쓰기 시작했다면 Esc로 멈추고 "문서부터 찾아 줘"라고 다시 지시합니다.

    2단계. AI 초안에서 흔히 나오는 실수 찾기¶

    아래는 문서를 보지 않고 쓰게 했을 때 실제로 나온 초안입니다(~/ws-solutions/cloudwan/policy/core-network-policy.ai-draft.json). 언뜻 보면 맞아 보입니다.

    {
  "version": "2021.12",
  "core-network-configuration": {
    "asn-ranges": ["64512-64700"],
    "edge-locations": [{ "location": "ap-northeast-2" }, { "location": "ap-northeast-1" }]
  },
  "segments": [
    { "name": "prod", "isolate": true },
    { "name": "dev-segment", "require-attachment-acceptance": false }
  ],
  "attachment-policies": [{
    "rule-number": 100,
    "conditions": [
      { "type": "attachment-type", "operator": "equals", "value": "transit-gateway-route-table" },
      { "type": "tag", "key": "segment", "value": "prod" }
    ],
    "action": { "association-method": "constant", "segment-name": "prod" }
  }]
}
    정답: 틀린 곳 6가지
    위치 문제 문서 기준
    asn-ranges 64512-64700 TGW ASN 64600·64601이 범위 안 → peering 불가 TGW ASN은 core network ASN 범위 밖이어야 함 (FAQ)
    "isolate": true 없는 키 isolate-attachments
    "dev-segment" 세그먼트 이름에 - 불가 a–z, A–Z, 0–9만
    조건 2개인데 condition-logic 없음 조건이 둘 이상이면 필수 "condition-logic": "and"
    "type": "tag" 없는 조건 유형 tag-value(+operator, key, value)
    "segment-name" 없는 키, 결과적으로 세그먼트 미지정 "segment": "prod"

    출처: Core network policy version parameters in AWS Cloud WAN, Create an attachment policy

    참고로 isolate-attachments: true는 같은 세그먼트 안의 attachment끼리도 막는 옵션입니다. "prod와 dev 격리"는 세그먼트를 나누는 것만으로 됩니다(세그먼트 간에는 share가 없으면 경로가 없음). 이름만 보고 쓰면 의미까지 틀리기 쉽습니다.

    Info

    문서 자체에도 흔들림이 있습니다. 예를 들어 같은 페이지에서 조건 유형을 tag-name/tag-value로 설명하면서 예시에는 tag-exists를 씁니다. 이럴 때는 "문서에 있다"로 끝내지 말고 서비스에 실제로 넣어 보는 것(아래 3단계 --live, 5-4 리허설)이 최종 판정입니다.

    3단계. 검사기를 AI에게 만들게 하기¶

    사람이 매번 표와 대조하기는 힘듭니다. 문서에서 허용 키 목록을 뽑아 오프라인 검사기를 만들게 합니다.

    Claude Code에 입력:

    policy JSON을 오프라인으로 검사하는 scripts/check_policy.py를 만들어 줘.
- 허용 키 목록은 방금 읽은 AWS 문서에서 가져오고, 파일 맨 위 주석에 출처 URL을 적어 줘. 기억으로 채우지 마.
- 검사: 모르는 키, 필수 필드(asn-ranges, 조건의 operator·value, 비어 있지 않은 action), version 값, 세그먼트 이름 규칙, 정의되지 않은 세그먼트 참조, 조건 유형/연산자,
  조건 2개 이상일 때 condition-logic, --tgw-asn으로 받은 TGW ASN이 asn-ranges와 겹치는지
- 성공 메시지는 "부분 검사 OK"로 해 줘. 이 검사기가 모든 것을 보지는 않으니까.
- 그리고 위 AI 초안을 policy/core-network-policy.ai-draft.json으로 저장해서 검사기가 잡는지 보여 줘.

    예상 출력:

    $ python3 scripts/check_policy.py policy/core-network-policy.ai-draft.json --tgw-asn 64600 --tgw-asn 64601
ERROR asn-ranges: TGW ASN 64600 falls in 64512-64700; peering would fail
ERROR asn-ranges: TGW ASN 64601 falls in 64512-64700; peering would fail
ERROR segments[0]: unknown key 'isolate'
ERROR segments[1].name: 'dev-segment' must be a-z, A-Z, 0-9 only
ERROR attachment-policies[0].condition-logic: required ('and'|'or') with more than one condition
ERROR attachment-policies[0].conditions[1].type: 'tag' unknown
ERROR attachment-policies[0].action: unknown key 'segment-name'
ERROR attachment-policies[0].action.segment: 'None' is not a defined segment
8 error(s)

$ python3 scripts/check_policy.py policy/core-network-policy.json --tgw-asn 64600 --tgw-asn 64601
부분 검사 OK (서비스 검증은 validate.sh --live)

    Warning

    검증 체크포인트 — 검사기도 AI가 만든 코드입니다

    • 검사기가 틀린 초안을 실패시키는지 먼저 봅니다(음성 대조). 통과만 보는 검사기는 아무것도 증명하지 않습니다.
    • 허용 키 목록 옆에 출처 URL이 있나요? 없으면 그 목록도 기억으로 쓴 것입니다.
    • 오프라인 검사는 "형식"만 봅니다. 최종 판정은 서비스가 합니다. core network가 있다면 정책을 새 버전으로 올리고(실행하지 않음) 결과를 봅니다.
    # core network가 있는 리허설 계정에서만. 새 policy version이 생기지만 LIVE로 적용되지는 않습니다.
aws networkmanager put-core-network-policy --region us-west-2 \
  --core-network-id <core-network-id> --policy-document file://policy/core-network-policy.json
aws networkmanager get-core-network-policy --region us-west-2 \
  --core-network-id <core-network-id> --policy-version-id <버전> \
  --query 'CoreNetworkPolicy.[ChangeSetState,PolicyErrors]'

    ChangeSetState가 READY_TO_EXECUTE이고 PolicyErrors가 비어 있을 때만 통과입니다. FAILED_GENERATION이면 PolicyErrors에 이유가 나옵니다. 검사용으로 만든 버전은 실행하지 않았으므로 지워 둡니다.

    aws networkmanager delete-core-network-policy-version --region us-west-2 \
  --core-network-id <core-network-id> --policy-version-id <버전>

    5단계의 validate.sh --live는 이 판정과 삭제를 자동으로 합니다(--keep을 주면 남김).

    4단계. CloudFormation은 정답을 복사해 검토하기¶

    시간 관계상 CloudFormation 템플릿 5개와 스크립트는 정답을 복사합니다. 대신 AI가 만든 IaC를 사람이 검토하는 연습을 합니다. 정답도 AI가 만든 것이라는 점을 기억하세요.

    cd ~/ws-cloudwan-workshop
mkdir -p static scripts
cp -r ~/ws-solutions/cloudwan/static/cfn static/
cp ~/ws-solutions/cloudwan/scripts/{validate.sh,deploy.sh,show-routes.sh,cleanup.sh} scripts/
ls static/cfn scripts
    템플릿 내용
    10-base-region.yaml 리전 하나분: VPC 2개(prod, dev), TGW(기본 연결/전파 끔, ASN 파라미터), prod / dev / peer RT
    20-tgw-peering.yaml Before: 서울 → 도쿄 TGW peering
    21-peering-routes.yaml Before: peering을 peer RT에 연결, prod RT·dev RT에 원격 CIDR 정적 경로
    30-cloudwan-core.yaml global network + core network (PolicyDocument 내장)
    40-cwan-tgw-peering.yaml 리전 하나분: core network와 TGW peering, prod RT·dev RT route table attachment(태그 segment)

    30-cloudwan-core.yaml의 PolicyDocument는 정답 정책입니다. 3단계에서 만든 내 policy/core-network-policy.json과 다르면 5단계 검사에서 잡힙니다. 어느 쪽에 맞출지는 직접 정하세요.

    Claude Code에 입력:

    static/cfn/의 템플릿을 리뷰해 줘. 고치지는 말고 표로만 보고해.
- 쓰인 리소스 타입과 속성이 CloudFormation 문서에 실제로 있는지 하나씩 확인하고 문서 URL을 붙여
- 리소스 태그에 Project=ws-ai-nssa가 빠진 곳
- cfn-lint static/cfn/*.yaml 결과

    Claude가 자주 놓치는 지점이 세 군데 있습니다. 리뷰 결과에 이 내용이 있는지, 템플릿에서 직접 찾아보세요.

    확인할 곳 맞는 값 근거
    TransitGatewayRouteTableAttachment의 속성 PeeringId, TransitGatewayRouteTableArn(ARN, ID 아님), Tags CFN 문서
    TransitGatewayPeering의 Ref peering ID(peering-…). TGW 쪽 attachment ID는 !GetAtt ….TransitGatewayPeeringAttachmentId CFN 문서
    TGW 쪽 policy table 콘솔은 peering을 만들 때 policy table을 새로 만들거나 고르게 하고, API로 만드는 AWS 예시는 peering 뒤에 따로 만들어 연결합니다. 템플릿에는 AWS::EC2::TransitGatewayPolicyTable + …Association이 있습니다. 꼭 필요한지는 리허설에서 확인 필요 Create a peering, 마이그레이션 블로그

    5단계. 한 번에 검증하기¶

    복사한 scripts/validate.sh는 AWS를 바꾸지 않는 검사를 한 번에 돌립니다. 3단계에서 만든 scripts/check_policy.py를 씁니다.

    1. cfn-lint static/cfn/*.yaml
    2. policy JSON 파싱 + check_policy.py
    3. 30-cloudwan-core.yaml 안의 PolicyDocument가 policy/core-network-policy.json과 같은지 비교
    4. (--live <core-network-id>일 때만) 서비스에 정책을 새 버전으로 올려 판정하고, 검사용 버전을 지움
    ./scripts/validate.sh

    예상 출력:

    == cfn-lint
OK
== policy
부분 검사 OK (서비스 검증은 validate.sh --live)
== template policy == policy file
OK

    Warning

    검증 체크포인트 — IaC

    • cfn-lint가 0개여도 배포가 된다는 뜻은 아닙니다. lint는 스키마만 봅니다. 서비스 순서 제약(예: peering이 AVAILABLE이 된 뒤에 route table attachment)은 리허설에서 확인합니다.
    • 3)번에서 MISMATCH가 나면 내 정책과 정답 정책이 다른 것입니다. 차이를 Claude에게 설명하게 하고, 어느 쪽이 문서에 맞는지 판단해 한쪽으로 맞춥니다.
    • 스크립트의 aws 명령에 --region이 빠진 곳이 없는지 grep -n "aws " scripts/*.sh로 직접 봅니다.
    • 스크립트를 Claude에게 리뷰시켜 보세요: "deploy.sh에서 병렬 배포가 실패해도 성공으로 넘어가는 곳이 있는지, cutover 전에 무엇을 확인하는지 설명해 줘."

    정답 예시: ~/ws-solutions/cloudwan/policy/, ~/ws-solutions/cloudwan/static/cfn/, ~/ws-solutions/cloudwan/scripts/
