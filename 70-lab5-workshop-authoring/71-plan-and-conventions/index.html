    5-1. 기획과 규약¶

    워크숍 제작에서 가장 비싼 실수는 "다 만들고 나서 대상이나 범위가 틀렸다는 것을 아는 것"입니다. 그래서 코드보다 먼저 스토리보드를 만들고 사람이 승인합니다. 이어서 저장소 규약(AGENTS.md)을 정해, 이후 Claude가 만드는 모든 파일이 같은 형식을 따르게 합니다.

    1단계. plan mode로 스토리보드 받기¶

    Shift+Tab을 두 번 눌러 plan mode로 바꿉니다(화면 아래에 plan mode on이 보입니다). plan mode에서는 Claude가 파일을 바꾸지 않고 조사와 계획만 합니다.

    Claude Code에 입력:

    고객 네트워크 엔지니어를 위한 "TGW에서 Cloud WAN으로 무중단 마이그레이션" 워크숍을 기획하려고 해.

- 대상: TGW 운영 경험은 있고 Cloud WAN은 처음인 엔지니어
- 시간: 2시간 30분, Workshop Studio로 진행
- 시작 환경: 서울(ap-northeast-2)과 도쿄(ap-northeast-1)에 TGW가 하나씩 있고 TGW 간 peering으로 연결.
  VPC는 prod-sel 10.1.0.0/16, dev-sel 10.2.0.0/16, prod-tyo 10.11.0.0/16, dev-tyo 10.12.0.0/16.
  각 TGW에 prod RT와 dev RT가 있어 prod/dev를 격리함.
- 목표 구조: Cloud WAN core network(edge 서울·도쿄, 세그먼트 prod·dev)에 각 TGW를 peering하고
  TGW route table attachment로 prod RT→prod, dev RT→dev 세그먼트에 붙인 뒤 TGW 간 peering을 제거.

모듈 목록(시간, 학습 목표, 각 모듈 끝에서 참석자가 확인할 값)을 표로 만든 스토리보드를 제안해 줘.
Cloud WAN 동작에 대한 설명은 AWS 문서를 찾아 근거 URL을 붙이고, 확인하지 못한 것은 "열린 질문"으로 따로 적어 줘.
비용이 나오는 모듈은 표시해 줘.

    Claude가 계획을 보여 주면 바로 승인하지 말고 다음을 확인합니다.

    Warning

    검증 체크포인트 — 스토리보드

    • 모듈마다 "끝에서 확인할 값"이 명령으로 확인 가능한 값인가요? ("이해한다"가 아니라 "attachment의 SegmentName이 prod" 같은 것)
    • ASN 이야기가 있나요? TGW ASN이 Cloud WAN의 asn-ranges 안에 있으면 peering을 만들 수 없습니다(Cloud WAN FAQ). 빠졌다면 추가를 요청하세요.
    • 전환(cut-over) 순서가 "Cloud WAN 경로가 들어온 뒤 → 정적 경로 삭제 → TGW peering 삭제"인가요?
    • 비용 표시: core network edge는 edge 하나에 시간당 요금이 붙습니다(요금).

    수정할 점을 말하고 다시 받습니다. 예:

    Claude Code에 입력:

    좋아. 두 가지만 바꿔 줘.
1) VPC를 Cloud WAN에 직접 붙이는 내용은 빼고 다음 워크숍으로 미뤄. 이번은 TGW를 유지하는 마이그레이션만.
2) 연결 확인은 EC2 ping 대신 TGW 라우팅 테이블(search-transit-gateway-routes)로 해. ping은 선택 과제로.
이대로 storyboard.md 파일로 저장해 줘.

    승인하면 Claude가 plan mode를 빠져나와 storyboard.md를 씁니다.

    예시 결과 보기 (~/ws-solutions/cloudwan/storyboard.md 일부)
    # 모듈 시간 핵심 확인
    0 시작 환경 배포 (Before) 20분 prod RT에 원격 prod CIDR만 있음
    1 Cloud WAN core network 만들기 25분 policy version EXECUTION_SUCCEEDED
    2 TGW를 Cloud WAN에 연결 30분 attachment SegmentName = prod/dev
    3 트래픽 전환 (cut-over) 20분 원격 CIDR 경로 유형 static → propagated
    4 격리 검증과 롤백 20분 dev RT에 prod CIDR 없음
    5 정리 10분 스택 0개
    Tip: 인터뷰 방식으로 기획하기 — /grill-with-docs

    요구 사항이 아직 흐릿하다면 프롬프트를 길게 쓰는 대신 /grill-with-docs로 Claude가 질문하게 할 수 있습니다. 대상, 시간, 범위, 용어("세그먼트", "route table attachment")를 하나씩 묻고, 정해진 용어는 GLOSSARY.md에, 결정("VPC 직접 연결은 다음 워크숍으로")은 ADR(docs/adr/)에 기록합니다. 워크숍 저장소처럼 오래 관리할 저장소라면 처음에 /setup-matt-pocock-skills를 한 번 실행해 둡니다. 설명: 1-6. Matt Pocock skills

    2단계. 워크숍 저장소 규약 정하기¶

    starter kit의 AGENTS.md는 "신규 기능 테스트" 저장소용입니다. 워크숍 저장소에는 Workshop Studio 구조와 문체 규칙이 더 필요합니다.

    Claude Code에 입력:

    이 폴더를 Workshop Studio 워크숍 저장소로 쓸 거야. 지금 AGENTS.md를 다음 내용이 들어가게 고쳐 줘.

- 구조: contentspec.yaml(ko-KR), content/<NN-module>/index.ko.md, static/images(구성도, 원본은 static/images/src),
  static/cfn(참석자가 배포하는 템플릿), policy/(core network policy 원본 JSON), scripts/(validate.sh, show-routes.sh, cleanup.sh)
- 리전: 서울 ap-northeast-2, 도쿄 ap-northeast-1. aws 명령에는 항상 --region.
  Network Manager API의 리전 요구 사항은 AWS 문서에서 확인해서 적어 줘.
- ASN: Cloud WAN 64512-64520, TGW 서울 64600, 도쿄 64601
- CloudFormation 스택 이름 접두어: ws-ai-nssa-cwan-
- 페이지 규칙: 합니다체, 목표 → 구성도 → 단계(명령 + 예상 출력) → 확인 → 정리.
  알림/탭/펼침은 Workshop Studio 문법. 비용이 나오는 단계 앞에는 warning 알림.
- 예상 출력은 리허설에서 받은 실제 출력으로 바꾸고, 그 전에는 <!-- 리허설 전 --> 주석을 남긴다.
- 정책 키와 CFN 속성은 문서로 확인한 것만 쓰고 모르면 TODO(확인 필요).
storyboard.md를 범위의 기준 문서로 적어 줘. 그리고 contentspec.yaml도 만들어 줘.

    Warning

    검증 체크포인트 — 규약

    • Network Manager 부분: Network Manager API 엔드포인트는 리소스가 어느 리전에 있든 us-west-2입니다(서비스 엔드포인트). 그래서 aws networkmanager ... 명령은 --region us-west-2로 부릅니다. Claude가 근거 URL 없이 다른 값을 적었다면 다시 확인을 요청하세요.
    • 참석자 셸의 AWS_REGION이 Bedrock용 us-east-1인 이유가 적혀 있나요? 이것을 모르면 리소스가 엉뚱한 리전에 생깁니다.

    왜 이렇게 하나요¶

    • 스토리보드 = 사람의 승인 지점. 이후 Claude에게 "storyboard.md 모듈 2를 써 줘"라고만 해도 범위가 고정됩니다. 대화가 길어져 /clear를 해도 파일은 남습니다.
    • AGENTS.md = 반복 지시의 저장소. "합니다체로", "--region 붙여" 같은 말을 매번 하지 않아도 됩니다. Codex 같은 다른 에이전트도 같은 파일을 읽습니다(CLAUDE.md는 @AGENTS.md 한 줄).
