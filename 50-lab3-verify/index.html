    Lab 3. Verify — 테스트 매트릭스 실행과 증적¶

    환경이 준비되었습니다. 이제 test-plan.md의 매트릭스를 실제 NLB에 대고 돌립니다. 이 Lab의 핵심은 "Claude가 성공했다고 말했다"가 아니라 "증적이 기대값과 같다" 로 결론을 내리는 것입니다.

    목표¶

    • 클라이언트 EC2에서 테스트 매트릭스를 실행합니다. Claude Code가 SSM Run Command로 직접 돌리게 합니다.
    • identity filter를 CLI로 적용하고, 필터 전후 결과를 비교합니다.
    • NLB access log의 tls_verify_status로 거부 사유를 확인합니다.
    • 기대값·실제값·근거가 들어간 results.md를 만들고, Lab 1의 "확인 필요" 항목을 닫습니다.

    라이프사이클에서의 위치¶

    단계 이 Lab에서 AI가 하는 일 사람이 판단할 일
    4 Verify 검증 테스트 실행, 로그 수집·파싱, 결과 표 정리 기대와 다른 결과의 원인 분류, 원본 증적과 요약 대조

    그림은 각 인증서가 NLB의 세 검사(신뢰 체인 → identity filter → CRL) 중 어디에서 걸리는지 보여 줍니다. 이 그림이 곧 기대값입니다. Lab 3이 끝나면 이 그림이 실제와 같은지 증적으로 말할 수 있어야 합니다.

    Info

    산출물: ~/ws-lab/scripts/run-on-client.sh, scripts/apply-filters.sh, scripts/fetch-logs.sh, ~/ws-lab/results.md

    1단계. Claude가 클라이언트에서 테스트를 돌릴 수 있게 하기¶

    클라이언트 EC2는 private subnet에 있고 SSH가 없습니다. Session Manager로 직접 들어가도 되지만, Claude Code가 명령을 보내고 출력을 받으려면 SSM Run Command 가 편합니다.

    Claude Code에 입력:

    scripts/run-on-client.sh를 만들어 줘.
- 사용법: scripts/run-on-client.sh <로컬 스크립트> [VAR=value ...]
- 스택 ws-ai-nssa-nlb-mtls 출력의 ClientInstanceId로 AWS-RunShellScript를 보내고, 스크립트는 base64로 실어 보내.
- 원격에서는 /etc/profile.d/lab.sh(NLB_DNS 등)를 source한 뒤 실행.
- 완료될 때까지 기다렸다가(시간 초과 있음) stdout/stderr, Status, ResponseCode를 출력.
- Status가 Success가 아니거나 시간 초과면 0이 아닌 코드로 끝내(원격 ResponseCode를 그대로 돌려줘). 그래야 실패가 호출자에게 보여.
- 모든 aws 명령에 --region "${LAB_REGION:-ap-northeast-2}", 공통 값은 scripts/lib.sh 사용.
만든 뒤 scripts/test-matrix.sh를 PHASE=base로 실행해 줘.

    기대하는 결과(필터 없음):

    case port 기대
    valid, no-eku, ou-staging, uri-only 443 ACCEPT
    no-cert, other-ca, revoked, eku-serverAuth, expired 443 REJECT
    plain:no-cert, plain:other-ca 8443 ACCEPT

    ERROR 행이 하나라도 있으면 테스트가 성립하지 않은 것입니다(인증서 파일 없음, DNS·연결 실패, 시간 초과 등). 결과를 해석하기 전에 원인부터 고칩니다.

    거부된 케이스의 curl 오류는 35 또는 56입니다. 리허설(클라이언트 curl 8.21.0, OpenSSL 3.5.8)에서 나온 메시지는 (56) Send failure: Connection reset by peer, (35) Recv failure: Connection reset by peer, (56) OpenSSL SSL_read: ... bad record type 세 가지였습니다. TLS 1.3에서는 클라이언트가 자기 쪽 핸드셰이크를 끝낸 뒤 NLB가 인증서를 거부하기 때문에(NLB mTLS 블로그), 같은 케이스도 실행할 때마다 35와 56이 바뀝니다. 그래서 판정은 HTTP 200 여부로 합니다.

    리허설 결과(2026-11-26): PHASE=base PASS 11 / FAIL 0. 실제 출력은 ~/ws-solutions/nlb-mtls/rehearsal.md에 있습니다.

    직접 들어가서 한 줄씩 해 보기 (Session Manager) 
    R="${LAB_REGION:-ap-northeast-2}"
IID=$(aws cloudformation describe-stacks --region "$R" --stack-name ws-ai-nssa-nlb-mtls \
  --query "Stacks[0].Outputs[?OutputKey=='ClientInstanceId'].OutputValue" --output text)
aws ssm start-session --region "$R" --target "$IID"

    클라이언트 안에서(인증서는 root 전용 폴더 /opt/lab/certs에 있으므로 sudo -i 먼저):

    sudo -i
source /etc/profile.d/lab.sh; cd /opt/lab/certs
# 정상
curl -sS --cacert lab-root-ca.pem --cert client-valid.pem --key client-valid.key \
  --connect-to mtls.lab.internal:443:$NLB_DNS:443 https://mtls.lab.internal/
# 핸드셰이크를 자세히: 서버가 보낸 CertificateRequest, acceptable CA names
openssl s_client -connect $NLB_DNS:443 -servername mtls.lab.internal -CAfile lab-root-ca.pem \
  -cert client-other-ca.pem -key client-other-ca.key -tls1_3 </dev/null 2>&1 | head -40

    2단계. identity filter 적용과 비교¶

    Lab 2에서 필터를 템플릿에 넣지 않았습니다. CLI로 적용합니다.

    Claude Code에 입력:

    scripts/apply-filters.sh를 만들어 줘. 사용법 on | off | show.
on이면 443 리스너에 client certificate identity filter 두 개를 OR로 적용해:
  subject-ou exact "Production", san-uri prefix "spiffe://lab.internal/ns/prod/"
필드·매치 값은 research.md(API 표기: subject-ou, san-uri, exact, prefix, action accept)를 따르고, Mode와 TrustStoreArn도 같이 보내.
off는 필터 목록을 빈 배열로, show는 describe-listeners의 MutualAuthentication.
on을 적용하고 show로 확인한 다음 test-matrix.sh를 PHASE=filter로 실행해 줘.

    필터 적용 후 달라지는 케이스는 하나(ou-staging)입니다. uri-only가 계속 통과하는지가 OR 동작의 증거입니다.

    Warning

    필터는 바로 반영되지 않습니다. modify-listener와 describe-listeners는 바로 새 필터를 돌려주지만, 리허설에서는 실제 연결에 반영되기까지 약 2분 16초 걸렸습니다. 적용 직후 4번 돌린 매트릭스는 모두 ou-staging이 ACCEPT로 남아 PASS 10 / FAIL 1이었습니다. 필터를 바꾼 뒤에는 3분 기다린 다음 PHASE=filter를 실행합니다. Claude가 이 FAIL을 "필터가 동작하지 않는다"로 결론 내리면, 시간을 두고 다시 돌려 보게 하세요.

    리허설 결과: 반영 뒤 PHASE=filter PASS 11 / FAIL 0.

    case 필터 전 필터 후 이유
    ou-staging ACCEPT REJECT OU=Staging, SAN.URI도 /ns/stg/ → 어떤 필터와도 안 맞음
    valid ACCEPT ACCEPT OU=Production (두 필터 모두 일치)
    no-eku ACCEPT ACCEPT OU=Production (SAN.URI는 없지만 OR)
    uri-only ACCEPT ACCEPT OU=Engineering으로 OU 필터는 불일치, SAN.URI …/ns/prod/sa/payments가 prefix 필터와 일치 → OR 동작 확인
    revoked REJECT REJECT 필터는 통과, 그다음 CRL에서 거부

    Warning

    aws elbv2 modify-listener가 ClientCertificateIdentityFilters를 모른다는 오류를 내면 AWS CLI가 오래된 것입니다. AWS CLI v2 2.41.2 이상이 필요합니다(CLI CHANGELOG의 elbv2 NLB mTLS 항목. 리허설은 2.42.4로 확인, 2.38.0에는 없음). aws --version과 aws elbv2 modify-listener help | grep ClientCertificateIdentityFilters로 확인하고 업데이트하세요.

    3단계. access log로 사유 확인¶

    NLB는 노드별로 5분마다 access log를 S3에 씁니다. 1–2단계를 끝내고 5–10분 기다린 뒤 수집합니다. 기다리는 동안 4단계의 메트릭을 먼저 봐도 됩니다.

    Claude Code에 입력:

    scripts/fetch-logs.sh를 만들어 줘. 스택의 LogsBucketName에서 nlb/AWSLogs/ 아래 로그를 ~/ws-lab/logs/raw로 sync하고,
최근 N분(기본 30) 항목에서 time, listener, client, tls_verify_status, leaf_client_cert_subject, leaf_client_cert_serial_number만 뽑아 Markdown 표로.
필드 순서는 NLB access log 문서의 필드 표를 그대로 따르고(따옴표로 묶인 subject 주의), 문서의 예시 로그 줄로 파서를 먼저 테스트해.
그다음 실제로 실행해서 test-matrix 케이스와 로그 행을 짝지어 줘. 거부된 행은 subject·serial이 "-"일 수 있으니 시각·포트·실행 순서로 짝짓고, 어떤 기준으로 짝지었는지 적어.
    • 거부 케이스마다 Failed:<코드>가 test-plan의 기대 코드와 같다.
    • 8443(mTLS off) 행은 leaf_client_cert_subject가 -다. tls_verify_status는 Success로 찍힙니다(리허설 확인).
    • 인증서 없음 케이스의 실제 코드를 확인해 "확인 필요"를 닫았다. 리허설에서는 Failed:ClientCertMissing이었습니다.

    리허설에서 본 로그의 특징입니다. Claude가 이와 다르게 요약하면 원본 행을 보여 달라고 하세요.

    케이스 tls_verify_status subject / serial
    valid, no-eku, uri-only Success 인증서 subject / 1001, 1006, 1003
    no-cert Failed:ClientCertMissing - / -
    other-ca Failed:ClientCertUntrusted - / -
    revoked Failed:ClientCertCrlHit - / -
    eku-serverAuth Failed:ClientCertPurposeInvalid - / -
    expired Failed:ClientCertExpired - / -
    ou-staging (필터 후) Failed:CertificateFilterNoMatch - / -
    8443 Success - / -

    거부된 연결은 subject와 serial이 남지 않습니다. "serial로 짝지었다"는 요약이 나오면 틀린 것입니다.

    Info

    파서를 만들 때 Claude에게 "문서의 예시 로그로 먼저 테스트하라"고 시킨 이유가 있습니다. 필드가 26개이고 subject에 공백과 쉼표가 들어 있어, 인덱스를 한 칸씩 잘못 세는 실수가 흔합니다. 이 워크숍의 정답 스크립트도 처음에는 한 칸 틀렸고, 문서 예시로 테스트해서 찾았습니다.

    4단계. 메트릭과 "확인 필요" 닫기¶

    블로그에는 mTLS 전용 CloudWatch 메트릭이 있다고 하지만, 메트릭 문서에는 이름이 없었습니다(Lab 1). AI에게 이름을 묻지 말고 실제 계정에서 확인합니다.

    리허설(2026-11-26, 배포 후 약 30분)에서는 이름에 Cert, Mutual, mTLS, Handshake가 들어간 지표가 하나도 없었습니다. mTLS 거부는 ClientTLSNegotiationErrorCount에 함께 세어졌습니다(매트릭스·장애 실습 뒤 Sum 115). TLS 관련 지표는 그 밖에 TargetTLSNegotiationErrorCount, NewFlowCount_TLS, ActiveFlowCount_TLS, ProcessedBytes_TLS, ConsumedLCUs_TLS였습니다. Claude가 블로그 문구를 근거로 지표 이름을 만들어 내는지 지켜보세요.

    Claude Code에 입력:

    AWS/NetworkELB 네임스페이스에서 우리 NLB(LoadBalancer 차원)에 실제로 발행된 메트릭 이름을 list-metrics로 모두 보여 주고,
mTLS·TLS·클라이언트 인증서와 관련 있어 보이는 것만 골라 최근 1시간 Sum을 get-metric-statistics로 보여 줘. 이름을 추측하지 마.
    선택: CloudFormation이 identity filter를 받아 주는지 change set으로 확인

    배포하지 않고 CloudFormation의 판단만 받아 볼 수 있습니다.

    Claude Code에 입력:

    /tmp/filters.yaml을 infra/nlb-mtls.yaml에서 복사해서 443 리스너 MutualAuthentication에 ClientCertificateIdentityFilters(apply-filters.sh와 같은 두 개)를 넣고,
스택 ws-ai-nssa-nlb-mtls에 대해 change set ws-ai-nssa-filter-check를 만들어서(기존 파라미터 재사용) 상태와 StatusReason만 보여 줘.
실행(execute)하지 말고, 확인이 끝나면 change set을 지워.

    결과(받아 줌 / 템플릿 오류 / 실행 단계에서만 알 수 있음)를 results.md의 "확인 필요" 표에 적습니다.

    리허설 결과: change set은 CREATE_COMPLETE(MtlsListener Modify, Replacement False)였습니다. 하지만 CloudFormation 레지스트리 스키마(aws cloudformation describe-type --type RESOURCE --type-name AWS::ElasticLoadBalancingV2::Listener)의 MutualAuthentication에는 이 속성이 없고 additionalProperties가 false입니다. change set을 만들 수 있다고 해서 실행이 성공한다는 뜻은 아닙니다. 그래서 "실행 단계에서만 알 수 있음"으로 적습니다. 정답 템플릿이 필터를 CLI로 적용하는 이유가 여기에 있습니다.

    선택: 만료 인증서 허용 (T11) 
    R="${LAB_REGION:-ap-northeast-2}"
L=$(aws cloudformation describe-stacks --region "$R" --stack-name ws-ai-nssa-nlb-mtls --query "Stacks[0].Outputs[?OutputKey=='MtlsListenerArn'].OutputValue" --output text)
TS=$(aws cloudformation describe-stacks --region "$R" --stack-name ws-ai-nssa-nlb-mtls --query "Stacks[0].Outputs[?OutputKey=='TrustStoreArn'].OutputValue" --output text)
aws elbv2 modify-listener --region "$R" --listener-arn "$L" \
  --mutual-authentication "Mode=verify,TrustStoreArn=$TS,IgnoreClientCertificateExpiry=true"

    expired 케이스가 ACCEPT로 바뀌는지 확인한 뒤 IgnoreClientCertificateExpiry=false로 되돌립니다. 이 명령은 필터 목록을 보내지 않습니다. 필터가 유지되는지, 지워지는지도 apply-filters.sh show로 확인해 보세요. 이런 동작은 문서보다 실제 결과가 더 정확한 근거가 됩니다.

    리허설 결과: 필터를 보내지 않아도 기존 필터 2개가 유지되었습니다. 반영까지는 켤 때 약 55초, 끌 때 약 62초 걸렸습니다.

    이 변경은 CloudFormation 밖에서 한 것이므로 스택에 드리프트가 생깁니다. 끝나면 원래 값으로 돌려놓으세요.

    5단계. 결과 보고서¶

    Claude Code에 입력:

    지금까지 실행한 명령 출력만 근거로 results.md를 써 줘. ~/ws-solutions/nlb-mtls/results-template.md의 구조를 따라도 돼.
- 매트릭스 표 두 개(PHASE=base, PHASE=filter)는 test-matrix.sh 출력을 그대로 붙여.
- access log 표와 케이스별 기대/실제 tls_verify_status 대조
- 기대와 다른 결과가 있으면 원인을 "문서/설정/테스트" 중 하나로 분류하고 근거를 적어.
- Lab 1의 "확인 필요" 항목마다 결과를 적고, 확인하지 못했으면 이유를 적어.
- 출력에 없는 숫자나 문장은 만들지 마.

    검증 체크포인트 — 요약을 믿어도 되는가¶

    AI 요약에서 가장 흔한 오류는 원본에 없는 내용이 매끄럽게 들어가는 것입니다.

    • results.md의 표 두 행을 골라, ~/ws-lab/logs/mtls-log-summary.md와 test-matrix 원본 출력에서 같은 값을 직접 찾았다.
    • "모두 성공" 같은 결론 문장 옆에 PASS/FAIL 개수가 있다.
    • 기대와 다른 결과가 0개라면, 일부러 하나를 틀리게 만들어(예: test-matrix.sh 기대값 하나 수정) 표가 ❌를 정말 표시하는지 확인했다. 실패를 잡지 못하는 테스트는 테스트가 아닙니다.

    정답 예시¶

    • ~/ws-solutions/nlb-mtls/scripts/run-on-client.sh, apply-filters.sh, fetch-logs.sh, test-matrix.sh
    • ~/ws-solutions/nlb-mtls/results-template.md (결과 틀. 실제 값은 직접 실행한 출력으로만 채웁니다)
