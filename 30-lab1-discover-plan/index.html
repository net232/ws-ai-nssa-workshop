    Lab 1. Discover & Plan — 신규 기능 조사와 테스트 계획¶

    2026년 11월에 Network Load Balancer mutual TLS(mTLS) 가 출시되었습니다. 고객이 "NLB에서 클라이언트 인증서로 접근을 막을 수 있나요? CRL은요? 특정 팀 인증서만 허용할 수 있나요?"라고 묻기 시작합니다. 답하려면 직접 테스트해 봐야 합니다.

    Lab 1–4에서는 이 신규 기능을 조사 → 설계 → 구축 → 검증 → 디버깅 순서로 끝까지 테스트합니다. Lab 1에서는 코드를 한 줄도 쓰지 않습니다. 대신 Claude Code와 함께 근거 있는 조사 노트와 사람이 승인한 테스트 계획서를 만듭니다.

    목표¶

    • 조사하기 전에 /grill-me로 테스트의 목표, 대상, 범위, 성공 기준을 정해 goal.md에 남깁니다.
    • 그 범위에 맞춰 AWS Knowledge MCP로 신규 기능의 공식 문서를 조사하고, 모든 주장에 출처 URL을 붙인 research.md를 만듭니다.
    • AI가 "문서끼리 다른 곳"과 "확인하지 못한 것"을 숨기지 않고 드러내게 합니다.
    • plan mode와 net-test-plan skill로 테스트 매트릭스·성공 기준·비용·정리 절차가 들어간 test-plan.md를 만듭니다.

    라이프사이클에서의 위치¶

    단계 이 Lab에서 AI가 하는 일 사람이 판단할 일
    1 Discover 목표·조사 목표 인터뷰, 그 범위에 맞춘 What's New·사용자 가이드·API·CloudFormation·쿼터·요금 조사, 출처 정리 목표와 범위 결정, 출처를 직접 열어 확인
    2 Plan 설계 테스트 매트릭스, 환경, 비용, 위험, 정리 절차 초안 시나리오 승인, 빠진 음성 케이스 추가

    테스트 환경 미리 보기¶

    Lab 2에서 만들 환경입니다. 계획을 세울 때 이 그림을 기준으로 이야기합니다.

    • ap-northeast-2, VPC 10.20.0.0/16, AZ 2개, private subnet에 internal NLB
    • TLS :443 리스너: mTLS verify (trust store = S3의 CA 번들 + CRL)
    • TLS :8443 리스너: mTLS off (같은 NLB에서 비교하는 대조군)
    • 대상 EC2 2대(TCP 8080), 클라이언트 EC2 1대(SSM Session Manager로 접속)

    Info

    모든 작업은 Module 1에서 만든 실습 폴더 ~/ws-lab에서 합니다. Lab 1 산출물: ~/ws-lab/goal.md, ~/ws-lab/research.md, ~/ws-lab/test-plan.md

    1단계. 세션 시작과 도구 확인¶

    cd ~/ws-lab
claude

    Claude Code에 입력:

    /mcp

    aws-knowledge(AWS Knowledge MCP)가 connected인지 확인합니다. 연결되어 있지 않으면 1-4. 확장 기능의 MCP 절을 다시 확인하세요.

    Info

    조사 단계에서는 AWS 계정을 바꾸는 명령이 필요 없습니다. Shift+Tab으로 plan mode에 두면 Claude가 파일을 쓰거나 명령을 실행하기 전에 계획부터 보여 줍니다.

    2단계. 목표 정하기: 무엇을 위해 테스트하는가¶

    조사부터 시작하면 범위가 끝없이 넓어집니다. 같은 NLB mTLS라도 목적에 따라 볼 것이 다릅니다. 고객 데모라면 거부 사유가 로그에 어떻게 남는지가 중요하고, 마이그레이션 검증이라면 기존 ALB mTLS와의 차이가 중요합니다. 먼저 목표를 정합니다.

    Claude Code에 입력:

    /grill-me 2026-11에 나온 NLB mutual TLS를 테스트하려고 해. 목적은 고객 데모와 사내 워크숍 소재야. 테스트 범위, 성공 기준, 쓸 수 있는 시간(오늘 Lab 1–4)과 비용을 같이 정해 줘. 결정이 끝나면 goal.md로 정리해.

    Claude가 번호 붙은 질문과 추천 답을 냅니다. 추천 답이 맞으면 yes로 받습니다. 두세 라운드면 충분합니다. 1단계에서 plan mode로 바꿨다면, 결정이 끝난 뒤 Claude가 보여 주는 goal.md 저장 계획을 승인해야 파일이 만들어집니다. 다음 단계로 가기 전에 ls -l ~/ws-lab/goal.md로 파일이 생겼는지 확인합니다. Matt Pocock skills를 설치하지 않았다면 /grill-me 대신 "질문을 하나씩 하면서 목표를 같이 정하자"라고 입력해도 됩니다.

    확인할 점

    goal.md에 다음 네 가지가 한 줄 이상씩 있는지 봅니다.

    • 목적(누구에게 무엇을 보여 주는가)
    • 범위(포함과 제외)
    • 성공 기준
    • 시간·비용 한도

    이 파일이 다음 단계의 조사 범위와 Lab 3의 판정 기준이 됩니다.

    3단계. 조사: 출처가 붙은 조사 노트 만들기¶

    Claude Code에 입력:

    2026년 11월에 출시된 Network Load Balancer mutual TLS(mTLS)를 조사해 줘.
goal.md의 목적과 범위에 맞춰, aws-knowledge MCP로 공식 문서만 찾아서 다음을 정리해 research.md로 저장해.

1. What's New 공지, 블로그, NLB 사용자 가이드(mutual authentication, configure, client certificate filters, access logs), 쿼터, API 레퍼런스
2. 지원 모드(verify/passthrough/off 중 NLB가 지원하는 것), 검사 순서, 클라이언트 인증서 요구 사항(EKU, KU, 체인 깊이, 크기)
3. CA 번들·CRL 파일 형식 규칙, identity filter의 필드·매치 방식·대소문자 규칙
4. access log에서 mTLS 결과를 보여 주는 필드와 오류 코드 전체
5. CLI 명령과 CloudFormation 리소스·속성 이름(정확한 철자)
6. ap-northeast-2 요금(가능하면 pricing 도구로)

규칙:
- 표의 모든 행에 출처 URL을 붙여. 문서에서 확인하지 못한 것은 "확인 필요"로 표시해.
- 문서끼리 서로 다르게 말하는 곳이 있으면 "문서 불일치" 절에 따로 모아.
- 추측으로 채우지 마.

    Claude가 search_documentation, read_documentation을 여러 번 호출하는 것이 보입니다.

    Warning

    plan mode에서는 파일이 저장되지 않습니다. 조사가 끝나면 Claude가 "research.md에 이렇게 쓰겠다"는 계획을 보여 주고 승인을 요청합니다. 내용을 훑어보고 승인해야 파일이 만들어집니다. 계획 없이 바로 저장하게 하려면 Shift+Tab으로 기본 모드로 돌아온 뒤 요청합니다.

    승인 후 파일이 생겼는지 확인하고 엽니다.

    ls -l ~/ws-lab/research.md && less ~/ws-lab/research.md
    선택: /research로 백그라운드 조사 돌리기 (Matt Pocock skills)

    조사가 길어질 것 같으면 /research를 쓰면 됩니다. 백그라운드 agent가 1차 출처로 조사하고, 주장마다 출처를 붙인 Markdown 파일을 저장합니다. 그동안 메인 세션에서는 4단계 계획을 먼저 생각해 둘 수 있습니다.

    Claude Code에 입력:

    /research NLB mutual TLS의 trust store 제약(CA 번들 형식, 인증서 체인 깊이, CRL 형식과 개수, 지원 키 알고리즘)과 access log 오류 코드를 AWS 공식 문서 기준으로 조사해서 notes/nlb-mtls-limits.md로 저장해 줘.

    끝났다는 알림이 오면 notes/nlb-mtls-limits.md를 research.md와 비교합니다. 두 결과가 다른 곳이 바로 직접 확인할 곳입니다. skill 설명은 1-6. Matt Pocock skills 활용을 참고하세요.

    검증 체크포인트 1 — 조사 노트를 믿어도 되는가¶

    AI가 만든 조사 노트에서 가장 위험한 것은 그럴듯하게 지어낸 사실입니다. 다음을 직접 확인합니다.

    • 출처 URL 중 3개를 골라 브라우저로 열고, 표의 내용이 그 페이지에 실제로 있는지 확인했다.
    • "NLB가 지원하는 모드"가 off, verify 두 가지로 적혀 있다. passthrough가 NLB에도 된다고 적혀 있으면 틀린 것입니다(ALB 전용).
    • EKU·KU 확장이 없는 인증서는 그 검사를 건너뛴다는 내용이 있다(Lab 3에서 직접 확인할 반직관적인 동작입니다).
    • access log 오류 코드에 ClientCertUntrusted, ClientCertCrlHit, ClientCertPurposeInvalid, ClientCertExpired, CertificateFilterNoMatch가 있다.
    • "문서 불일치" 절이 있다. 없다면 다음 프롬프트로 다시 묻습니다.

    Claude Code에 입력:

    CloudFormation 템플릿 레퍼런스의 AWS::ElasticLoadBalancingV2::Listener MutualAuthentication 속성 목록과,
NLB 사용자 가이드 client certificate filters 페이지의 CloudFormation 예시를 직접 비교해 줘.
ClientCertificateIdentityFilters가 양쪽에 다 있는지, 필드 값 표기(Subject.CN vs subject-cn)는 어떤지 출처와 함께 research.md의 "문서 불일치"에 추가해.

    Warning

    출시 직후 기능에서는 문서끼리 다른 경우가 흔합니다. 이 워크숍 작성 시점(2026-11-26)에는 사용자 가이드가 CloudFormation 예시에 ClientCertificateIdentityFilters를 보여 주지만, CloudFormation 템플릿 레퍼런스와 cfn-lint에는 이 속성이 없었습니다. 이런 차이를 찾는 것까지가 조사입니다. 어느 쪽을 따를지는 사람이 정합니다. 워크숍 전 리허설에서는 계정의 CloudFormation 레지스트리 스키마에도 이 속성이 없었습니다(Lab 2 함정 B).

    강사용: '확인 필요' 항목의 리허설 결과 (2026-11-26)

    참석자가 Lab 3에서 직접 닫을 항목입니다. 미리 알려 주지 말고, 결과를 비교할 때 씁니다.

    항목 리허설 결과
    인증서 없음 사유 코드 Failed:ClientCertMissing
    mTLS 전용 CloudWatch 메트릭 배포 후 30분 동안 없음. 거부는 ClientTLSNegotiationErrorCount에 세어짐
    CFN ClientCertificateIdentityFilters cfn-lint E3002, 레지스트리 스키마에 없음. change set은 생성됨(실행 결과는 미확인)
    CA 번들 교체 시 기존 CRL revocation이 그대로 남음

    자세한 내용은 ~/ws-solutions/nlb-mtls/rehearsal.md에 있습니다.

    4단계. 설계: plan mode와 skill로 테스트 계획서 만들기¶

    Shift+Tab을 눌러 plan mode인지 확인한 뒤, Claude Code에 입력:

    /net-test-plan goal.md와 research.md를 근거로 NLB mTLS 테스트 계획서를 test-plan.md로 만들어 줘.

환경: ap-northeast-2, VPC 10.20.0.0/16 (AZ 2개), internal NLB, TLS 443 = mTLS verify(trust store + CRL), TLS 8443 = mTLS off(대조군),
대상 EC2 2대(TCP 8080), 클라이언트 EC2 1대(SSM). 서버 인증서는 우리 lab CA가 발급해 ACM에 import.

테스트 매트릭스에는 최소한 다음을 넣어:
정상 클라이언트 / 인증서 없음 / 다른 CA / CRL로 폐기 / EKU가 serverAuth뿐 / EKU·KU 없음 / 만료 /
identity filter(OU exact + SAN.URI prefix) 불일치와 일치 / OU는 다르고 SAN.URI만 맞는 인증서(OR 동작 확인) / 8443 대조군.
각 케이스에 기대 결과와 관찰 방법(명령, access log의 tls_verify_status 값)을 적고,
ap-northeast-2 시간당 비용, 위험, 정리 순서도 넣어. 산출물 경로는 test-plan.md로 해.

    Claude가 계획을 먼저 보여 줍니다. 계획을 읽고 승인하기 전에 빠진 것을 말해 줍니다. 예:

    좋아. 다만 IgnoreClientCertificateExpiry=true로 바꾼 뒤 만료 인증서가 통과하는지 보는 선택 케이스를 추가해 줘.
그리고 access log는 5분 단위로 전달되니까 관찰 방법에 수집 시점을 적어.

    승인하면 plan mode가 풀리고 test-plan.md가 저장됩니다. ls -l ~/ws-lab/test-plan.md로 확인합니다.

    Info

    net-test-plan skill은 계획서를 test-plan.md에 저장합니다. 다른 경로가 필요하면 프롬프트로 지정하면 됩니다. skill은 절차를 정해 줄 뿐이고, 그 자리에서 사람이 주는 지시가 우선합니다.

    선택: /grill-me로 테스트 계획을 인터뷰받기 (Matt Pocock skills)

    /grill-me는 계획을 집요하게 인터뷰합니다. 결정할 것을 트리로 펼치고, 질문마다 추천 답을 함께 냅니다. 계획서를 쓰기 전에 "무엇을 왜 테스트하는가"를 정리할 때 좋습니다.

    Claude Code에 입력:

    /grill-me 신규 출시된 NLB mTLS를 고객 데모와 워크숍 소재로 테스트하려고 해. research.md를 읽고, internal NLB 하나에 클라이언트 인증서를 여러 종류로 바꿔 가며 허용/거부와 로그 사유 코드를 확인할 계획이야.

    인터뷰가 끝나면 정해진 결정을 /net-test-plan 프롬프트에 붙여 계획서를 만듭니다. 자세한 사용법은 1-6. Matt Pocock skills 활용을 참고하세요.

    검증 체크포인트 2 — 계획서를 승인해도 되는가¶

    • 모든 테스트 케이스에 기대 결과와 관찰 방법이 있다. "잘 되는지 확인" 같은 문장은 관찰 방법이 아닙니다.
    • 거부되어야 하는 음성 케이스가 허용 케이스보다 많다.
    • 반직관적인 케이스(EKU·KU 없음 → 허용)가 들어 있다.
    • 필터의 OR 동작을 확인하는 케이스(OU 불일치 + SAN.URI 일치 → 허용)가 있다. 허용 케이스가 하나뿐이면 "필터가 OU만 보는지"를 구별할 수 없습니다.
    • 비용 표에 NAT Gateway와 trust store 시간 요금이 있다(ap-northeast-2 $0.005/h, Price List API).
    • 정리 순서에 "로그 버킷을 먼저 비운다", "ACM에 import한 인증서를 지운다"가 있다.
    • research.md의 "확인 필요" 항목이 계획서의 확인 대상으로 넘어와 있다.

    정답 예시¶
