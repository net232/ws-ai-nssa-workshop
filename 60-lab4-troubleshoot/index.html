    Lab 4. Troubleshoot — 장애 주입과 AI 진단¶

    새 기능을 고객에게 소개하면 곧 "안 되는데요"라는 연락이 옵니다. Lab 4에서는 정상 동작하는 환경에 장애를 하나 몰래 주입하고, Claude Code와 함께 원인을 찾습니다. 목표는 AI가 답을 맞히는 것이 아닙니다. 증거로 원인을 좁혀 가는 과정을 AI와 함께 밟는 것입니다.

    목표¶

    • 증상을 재현하는 "실패하는 명령 하나"부터 만들고, 가설 → 증거 → 원인 → 수정 → 재확인 순서로 진단합니다.
    • 원인을 찾기 전까지 Claude가 읽기 전용 명령만 쓰도록 통제합니다.
    • 대조군(8443, mTLS off)과 access log 사유 코드로 문제 범위를 빠르게 나눕니다.
    • 진단 과정을 rca.md로 남깁니다.

    라이프사이클에서의 위치¶

    단계 이 Lab에서 AI가 하는 일 사람이 판단할 일
    5 Troubleshoot 디버깅 증상 재현, 가설 목록, describe·로그·Reachability Analyzer로 증거 수집 근본 원인 확정, 수정 승인, 재발 방지

    inject-fault.sh는 그림의 ①–④ 중 하나를 바꿉니다. 겉으로는 모두 "연결이 안 된다"로 보이지만 남는 증거가 다릅니다.

    Info

    시작 상태: Lab 3을 마친 상태(identity filter 켜짐). 기준선은 scripts/run-on-client.sh scripts/test-matrix.sh PHASE=filter 결과가 FAIL 0입니다. 산출물: ~/ws-lab/rca.md

    1단계. 장애 주입¶

    정답 스크립트를 가져와 짝꿍(또는 강사)이 번호를 고르거나, 스스로 무작위로 주입합니다. 어떤 장애인지 보지 마세요.

    cp ~/ws-solutions/nlb-mtls/scripts/{inject-fault.sh,fix-fault.sh} ~/ws-lab/scripts/
cd ~/ws-lab
scripts/inject-fault.sh random

    출력은 "장애를 주입했습니다" 한 줄뿐입니다. 3분쯤 기다립니다. 리허설에서는 장애 2–4가 연결에 반영되기까지 45–63초 걸렸고, 장애 1만 즉시 반영되었습니다.

    Warning

    inject-fault.sh와 fix-fault.sh를 Claude Code에게 읽게 하지 마세요. 답이 들어 있습니다. 이번 세션에서는 scripts/inject-fault.sh, scripts/fix-fault.sh를 읽지 말라고 첫 프롬프트에서 분명히 말합니다.

    2단계. 진단 규칙을 정하고 시작하기¶

    새 세션을 열고(/clear) plan mode로 둡니다. 첫 프롬프트에서 진단 규칙을 줍니다.

    Claude Code에 입력:

    NLB mTLS 테스트 환경(스택 ws-ai-nssa-nlb-mtls, ap-northeast-2)에 장애가 생겼어. 원인을 같이 찾자.
규칙:
1. scripts/inject-fault.sh, scripts/fix-fault.sh, .lab-state는 읽지 마.
2. 원인을 확정하기 전에는 읽기 전용 명령(describe-*, get-*, list-*, s3 sync로 로그 내려받기, test-matrix 실행)만 써. 바꾸는 명령은 내가 승인한 뒤에.
3. 먼저 증상을 재현하는 "실패하는 명령 하나"를 정하고 그 출력을 보여 줘.
4. 가설은 표로: 가설 / 이 가설이 맞다면 보일 증거 / 확인 명령 / 결과 / 판정.
5. 대조군(8443, mTLS off) 결과와 access log의 tls_verify_status를 꼭 이용해.
시작: scripts/run-on-client.sh scripts/test-matrix.sh PHASE=filter 를 실행하고 기준선(test-plan.md)과 다른 행을 알려 줘.

    Claude가 범위를 좁혀 가는 과정을 지켜봅니다. 다음 질문으로 방향을 잡아 줄 수 있습니다.

    질문 왜
    "8443은 되는데 443만 안 되는가?" 네트워크·대상 문제인지 mTLS 검사 문제인지 한 번에 나눕니다.
    "정상 인증서만 안 되는가, 다른 것도 결과가 바뀌었나?" 다른 CA 인증서가 갑자기 통과한다면 trust store 쪽입니다.
    "ERROR 행이 있는가?" ERROR는 NLB가 거부한 것이 아니라 테스트가 성립하지 않은 것(시간 초과, 연결 실패)입니다. 대상 경로 문제의 단서가 됩니다.
    "access log의 사유 코드는?" ClientCertUntrusted, ClientCertCrlHit, CertificateFilterNoMatch는 각자 다른 곳을 가리킵니다.
    "target health는?" unhealthy면 mTLS와 무관한 경로 문제입니다.
    선택: diagnosing-bugs로 피드백 루프부터 만들기 (Matt Pocock skills)

    diagnosing-bugs skill은 가설부터 세우지 않습니다. 먼저 "이 버그에서 실패하는 명령 하나", 즉 빠르게 반복 실행할 수 있는 피드백 루프를 만들고, 그다음에 원인을 좁힙니다. 출력에 들어 있는 비밀 값은 가려 줍니다.

    Claude Code에 입력:

    /diagnosing-bugs NLB mTLS 443 리스너에서 정상 클라이언트 인증서(client-valid) 연결이 갑자기 실패해. 8443은 확인 전이야.
피드백 루프는 scripts/run-on-client.sh로 클라이언트 EC2에서 실행하는 한 줄로 만들어 줘.
정상 인증서로 https://mtls.lab.internal/ 에 요청해서 HTTP 200이면 PASS, 아니면 FAIL과 curl 종료 코드를 출력하고 0이 아닌 값으로 끝나야 해.
예: curl -sS -o /dev/null -w '%{http_code}' --max-time 5 --connect-to mtls.lab.internal:443:$NLB_DNS:443 --cacert ... --cert client-valid.pem --key client-valid.key
TLS 1.3에서는 거부가 핸드셰이크 뒤에 오므로 연결 성공만으로 PASS 처리하지 마. inject-fault.sh / fix-fault.sh / .lab-state는 읽지 마.

    이 skill은 요청이 description과 맞으면 Claude가 스스로 불러오기도 합니다. 자세한 내용은 1-6. Matt Pocock skills 활용을 참고하세요.

    3단계. 증거 수집 도구¶

    Claude가 쓸 만한 읽기 전용 명령입니다. Claude가 고른 명령이 무엇을 보는지 이해하는 데 쓰세요.

    R="${LAB_REGION:-ap-northeast-2}"; S=ws-ai-nssa-nlb-mtls
out() { aws cloudformation describe-stacks --region "$R" --stack-name "$S" --query "Stacks[0].Outputs[?OutputKey=='$1'].OutputValue" --output text; }

# 대상 상태
aws elbv2 describe-target-health --region "$R" --target-group-arn "$(out TargetGroupArn)"
# 리스너 mTLS 설정(필터 포함)
aws elbv2 describe-listeners --region "$R" --listener-arns "$(out MtlsListenerArn)" --query 'Listeners[0].MutualAuthentication'
# trust store와 revocation
aws elbv2 describe-trust-stores --region "$R" --trust-store-arns "$(out TrustStoreArn)"
aws elbv2 describe-trust-store-revocations --region "$R" --trust-store-arn "$(out TrustStoreArn)"
# trust store에 실제로 올라간 CA 번들을 원본과 비교 (subject + SHA-256 fingerprint)
curl -s "$(aws elbv2 get-trust-store-ca-certificates-bundle --region "$R" --trust-store-arn "$(out TrustStoreArn)" --query Location --output text)" \
  | openssl x509 -noout -subject -fingerprint -sha256
openssl x509 -in certs/ca-bundle.pem -noout -subject -fingerprint -sha256     # 기준 값
# 보안 그룹 규칙
aws ec2 describe-security-group-rules --region "$R" --filters Name=group-id,Values="$(out TargetSecurityGroupId)"
# CloudFormation 밖에서 바뀐 것 (참고용: 모든 변경을 잡지는 못함, 아래 주의)
aws cloudformation detect-stack-drift --region "$R" --stack-name "$S"
# access log (5분 지연)
scripts/fetch-logs.sh 20

    Warning

    드리프트 감지는 "바뀌지 않았다"의 증거가 되지 못합니다. 예를 들어 TrustStore의 CA 번들 S3 속성은 writeOnly일 수 있어, 번들 내용이 바뀌어도 드리프트로 나오지 않을 수 있습니다. trust store는 실제로 올라간 번들의 fingerprint를 원본과 비교하는 것이 결정적 증거입니다.

    Reachability Analyzer로 NLB → 대상 경로 확인

    NLB 노드의 ENI에서 대상 인스턴스 8080까지 경로를 분석합니다. 분석 1회마다 요금이 있습니다(Amazon VPC 요금 페이지의 Network Reachability Analyzer 항목).

    Claude Code에 입력:

    Reachability Analyzer로 NLB(ws-ai-nssa-mtls)의 ENI 하나에서 backend A 인스턴스 TCP 8080까지 경로를 분석해 줘.
NLB ENI는 description이 "ELB net/ws-ai-nssa-mtls/"로 시작하는 것. path와 analysis를 만들고, 결과의 NetworkPathFound와 Explanations만 요약해.
끝나면 path와 analysis를 지워도 되는지 나에게 물어봐.

    경로가 막혔다면 Explanations에 막은 보안 그룹과 규칙 방향이 나옵니다.

    4단계. 수정과 재확인¶

    원인이 확정되면 Claude에게 수정 명령을 제안하게 하고, 사람이 승인합니다.

    Claude Code에 입력:

    원인이 확정됐다면 근거 두 가지와 함께 한 문장으로 말해 줘. 그리고 되돌리는 명령을 제안만 해(아직 실행하지 마).
그 명령이 CloudFormation 드리프트를 남기는지도 알려 줘.

    승인하고 실행한 뒤, 처음 정한 "실패하는 명령" 과 매트릭스 전체로 다시 확인합니다. trust store·필터 변경은 반영에 1–2분 걸립니다(리허설 45–79초). 고친 직후 FAIL이 1개 남아도 바로 다른 원인을 찾지 말고, 1–2분 뒤 다시 돌립니다.

    scripts/run-on-client.sh scripts/test-matrix.sh PHASE=filter   # FAIL 0

    검증 체크포인트 — 진단을 믿어도 되는가¶

    • 근본 원인 하나를 서로 다른 종류의 증거 두 개 이상(예: 사유 코드 + 설정 조회)이 뒷받침한다.
    • 기각한 가설에도 확인 명령과 결과가 있다. "아마 아닐 것"으로 넘어간 가설이 없다.
    • 수정 후 처음의 실패 명령이 성공했고, 매트릭스가 FAIL 0이다.
    • 마지막으로 scripts/fix-fault.sh의 해당 번호 설명(정답)과 내 결론이 같은지 비교했다. 이미 복구했으면 fix-fault.sh가 같은 변경을 한 번 더 적용하려다 오류를 낼 수 있으니, 정답 확인은 파일을 읽어서 합니다.

    5단계. RCA 남기기¶

    Claude Code에 입력:

    이번 진단을 rca.md로 정리해 줘. 증상, 재현 명령, 범위 좁히기, 가설 표(확인 명령과 실제 출력 발췌), 근본 원인, 조치, 재확인, 재발 방지.
출력에 없는 내용은 쓰지 마. ~/ws-solutions/nlb-mtls/rca-example.md의 구조를 참고해도 돼.

    시간이 남으면 .lab-state의 장애 기록이 비었는지 확인하고(fix-fault.sh를 쓰지 않고 직접 고쳤다면 grep fault ~/ws-lab/.lab-state로 보고 fault= 줄을 비웁니다) 다른 장애를 하나 더 주입해 반복합니다.

    강사용: 장애별 증상과 결정적 증거
    # 주입 매트릭스 증상(PHASE=filter) 8443 결정적 증거 복구
    1 target SG에서 NLB SG → TCP 8080 인바운드 제거 통과해야 할 valid·no-eku·uri-only가 ERROR(curl 28, 시간 초과). 거부 케이스 6개는 그대로 REJECT → PASS 6 / FAIL 5 ERROR(curl 28) access log는 valid 등이 Success(connection_time 약 7,000 ms, 바이트 0) → "mTLS는 무죄". target health 약 45초 뒤 unhealthy(Target.FailedHealthChecks), SG 인바운드 규칙 없음 SG 규칙 복원. 즉시 회복(대상이 아직 unhealthy여도 fail-open으로 통과), 약 20초 뒤 healthy
    2 trust store CA 번들을 rogue CA로 교체 valid·no-eku·uri-only REJECT, other-ca ACCEPT(OU=Production이라 필터도 통과) → PASS 7 / FAIL 4 정상 Failed:ClientCertUntrusted(revoked·expired도 Untrusted. 신뢰 체인 검사가 먼저), other-ca는 Success와 subject. 올라간 번들 subject가 CN=ws-ai-nssa rogue CA이고 SHA-256 fingerprint가 certs/ca-bundle.pem과 다름 modify-trust-store로 원래 번들
    3 client-valid를 폐기한 CRL 추가 valid만 REJECT → PASS 10 / FAIL 1 정상 Failed:ClientCertCrlHit, revocation 2개(ID 2는 2건: client-revoked와 serial 1001), TotalRevokedEntries 3 추가된 revocation ID 제거
    4 필터 값 오타(OU Prod)와 SAN.URI 경로 대소문자(/NS/prod/) valid·no-eku·uri-only REJECT → PASS 8 / FAIL 3 (uri-only는 SAN.URI 경로가 대소문자를 구분한다는 증거) 정상 Failed:CertificateFilterNoMatch, describe-listeners의 필터 값. revoked도 CertificateFilterNoMatch로 바뀜(필터가 CRL보다 먼저) 올바른 필터 재적용

    리허설(2026-11-26)에서 확인한 것:

    • 장애 1은 REJECT가 아니라 ERROR로 보입니다. mTLS 검사는 NLB에서 끝나고 대상 연결만 막히기 때문입니다. 그래서 Claude가 "모든 연결이 거부된다"고 요약하면 틀린 것입니다.
    • 장애 2에서 CA 번들을 바꿔도 기존 CRL(revocation ID 1, lab CA가 발급, 1건)은 그대로 남았습니다. modify-trust-store는 성공하고 trust store는 ACTIVE입니다. 번들을 되돌리면 revoked는 다시 ClientCertCrlHit으로 거부됩니다.
    • 거부된 연결의 access log에는 subject와 serial이 -로 남습니다. 장애 3에서 "serial 1001이 거부되었다"는 로그가 아니라 CRL 내용(openssl crl -text)과 test-matrix 결과로 말해야 합니다.

    정리와 팁¶

    • 바꾸기 전에 보기만 하게 하세요. 진단 중 Claude가 "고쳐 볼게요"라고 설정을 바꾸면 원래 증거가 사라집니다. 규칙 2는 그래서 있습니다. starter kit의 권한 설정(ask)도 같은 역할을 합니다.
    • 대조군이 진단 시간을 줄입니다. 8443 리스너 하나 덕분에 "네트워크냐 mTLS냐"를 명령 한 번으로 나눴습니다. 테스트 환경을 설계할 때부터 대조군을 넣으세요(Lab 1).
    • 사유 코드가 있는 서비스는 사유 코드부터. NLB mTLS는 거부 이유를 access log에 남깁니다. 5분 지연이 있으니, 기다리는 동안 설정 조회를 병렬로 진행합니다.
