    Lab 2. Build — 인증서와 IaC 만들기¶

    Lab 1에서 승인한 test-plan.md를 실제 환경으로 만듭니다. Claude Code가 인증서 생성 스크립트와 CloudFormation 템플릿을 쓰고, 사람은 AI가 지어낸 속성과 값을 걸러 내는 일에 집중합니다.

    목표¶

    • 테스트 매트릭스의 모든 케이스에 맞는 인증서를 openssl로 만들고, 배포 전에 로컬에서 리허설합니다.
    • 테스트 환경 CloudFormation을 만들고 cfn-lint와 문서 대조로 검증합니다.
    • "lint는 통과하지만 배포에서 실패하는" 환각과 "문서에는 있지만 lint가 거부하는" 속성을 구별합니다.
    • 업로드·ACM import·배포를 스크립트 하나로 묶어 배포합니다.

    라이프사이클에서의 위치¶

    단계 이 Lab에서 AI가 하는 일 사람이 판단할 일
    3 Build 구축 gen-certs.sh, infra/nlb-mtls.yaml, deploy.sh 작성, cfn-lint 실행·수정 보안(키 보관, SG 범위)·비용 검토, 문서 대조
    4 Verify 검증(앞당김) 로컬 openssl s_server 리허설 리허설 결과가 계획의 기대값과 같은지 확인

    시간이 부족하면: 정답 스크립트를 복사하고 검증에 집중

    이 Lab에서 만들 파일이 많습니다(인증서 도구, 리허설, 템플릿, 배포 스크립트). 20분이 지나도 1단계를 끝내지 못했다면 정답을 복사해 배포를 먼저 시작하고, 사람은 검증에 집중합니다. 배포가 도는 5분 동안 3단계의 cfn-lint, 함정 A·B, 검증 체크포인트를 진행하면 됩니다.

    cp -r ~/ws-solutions/nlb-mtls/{infra,scripts} ~/ws-lab/
cd ~/ws-lab && OUT_DIR=~/ws-lab/certs scripts/gen-certs.sh && scripts/local-rehearsal.sh
scripts/deploy.sh          # 배포 시작 (5분 안팎, 리허설 4분 11초)
cfn-lint infra/nlb-mtls.yaml

    복사한 파일도 "남이 쓴 코드"입니다. Claude에게 infra/nlb-mtls.yaml의 mTLS 관련 속성마다 근거 문서 URL을 달아 줘라고 시켜 검증 체크포인트 2를 그대로 진행하세요.

    Info

    산출물: ~/ws-lab/scripts/gen-certs.sh, scripts/local-rehearsal.sh, scripts/deploy.sh, infra/nlb-mtls.yaml, 인증서는 ~/ws-lab/certs/(git 제외). CloudFormation 스택 이름: ws-ai-nssa-nlb-mtls

    1단계. 인증서 도구 만들기¶

    Claude Code에 입력:

    test-plan.md의 테스트 매트릭스에 필요한 인증서를 만드는 scripts/gen-certs.sh를 작성해 줘.

- 출력 폴더는 OUT_DIR(기본 ~/ws-lab/certs). 폴더가 이미 있으면 FORCE=1 없이는 지우지 말고, /, $HOME, ~/ws-lab 같은 위험한 경로는 거부해.
- CA 두 개: lab-root-ca(trust store에 올림), rogue-ca(올리지 않음)
- 서버 인증서: CN/SAN = mtls.lab.internal, EKU serverAuth, lab-root-ca가 서명 (ACM import용 chain 파일도)
- 클라이언트: client-valid(OU=Production, SAN DNS + URI spiffe://lab.internal/ns/prod/sa/orders, EKU clientAuth),
  client-staging(OU=Staging, spiffe://lab.internal/ns/stg/...),
  client-uri-only(OU=Engineering, SAN URI spiffe://lab.internal/ns/prod/sa/payments — 필터 OR 확인용), client-revoked, client-eku-server(EKU serverAuth만),
  client-no-eku(EKU·KU 확장 없음), client-expired(과거 기간), client-other-ca(rogue-ca가 서명)
- client-revoked를 폐기한 CRL을 PEM으로. serial은 양수로.
- trust store용 ca-bundle.pem은 NLB CA 파일 규칙(PEM 블록만, 빈 줄·텍스트 금지)을 지켜.
- Lab 4에서 쓸 ca-bundle-wrong.pem(rogue CA)도 만들어.
research.md의 인증서 요구 사항을 근거로 쓰고, 다 만들면 실행해서 결과를 보여 줘.

    Info

    과거 날짜 인증서와 CRL이 필요하므로 Claude는 보통 openssl x509 -req 대신 openssl ca(CA 데이터베이스 사용)를 고릅니다. 다른 방법을 골라도 아래 검증만 통과하면 됩니다.

    검증 체크포인트 1 — 인증서가 의도대로 만들어졌는가¶

    Claude에게 "확인해 줘"라고만 하지 말고, 무엇을 어떻게 볼지 정해 줍니다.

    Claude Code에 입력:

    certs/의 클라이언트 인증서마다 subject, issuer, notAfter, EKU, KU, SAN을 한 줄씩 표로 보여 주고,
openssl verify -CAfile certs/ca-bundle.pem -CRLfile certs/crl.pem -crl_check -purpose sslclient 결과를 같이 보여 줘.
test-plan.md의 기대 결과와 다른 인증서가 있으면 표시해.

    기대하는 결과:

    인증서 openssl verify 이유
    client-valid, client-staging, client-uri-only, client-no-eku OK client-no-eku는 EKU·KU가 없으므로 용도 검사를 건너뜀
    client-other-ca 실패 다른 CA
    client-revoked 실패 CRL
    client-eku-server 실패 용도(EKU)
    client-expired 실패 만료
    • ca-bundle.pem이 -----BEGIN CERTIFICATE-----로 시작하고 빈 줄이 없다(grep -c '^$' certs/ca-bundle.pem → 0).
    • certs/가 .gitignore에 들어 있다. 개인 키는 커밋하지 않습니다.

    2단계. 배포 전 로컬 리허설¶

    AWS에 올리기 전에, 같은 인증서로 로컬 openssl s_server를 띄워 매트릭스를 돌려 봅니다. 클라우드에서 실패했을 때 "인증서 문제인가, AWS 설정 문제인가"를 나눌 수 있게 됩니다.

    Claude Code에 입력:

    scripts/test-matrix.sh를 먼저 만들어 줘. 클라이언트 EC2에서 돌릴 스크립트야.
- 환경 변수 NLB_DNS, SERVER_NAME(mtls.lab.internal), CERTS(기본 /opt/lab/certs), PHASE(base|filter), MTLS_PORT(443), PLAIN_PORT(8443)
- curl --connect-to로 SERVER_NAME을 NLB_DNS에 연결하고 --cacert lab-root-ca.pem으로 서버 인증서도 검증해(-k 쓰지 마).
- 판정: curl 종료 코드 0이고 HTTP 200이면 ACCEPT, TLS 단계에서 끊기면(curl 35/52/55/56) REJECT,
  그 밖의 경우(인증서 파일 없음, DNS·연결 실패, 시간 초과, 서버 인증서 검증 실패)는 ERROR로 표시하고 FAIL로 세.
- 케이스마다 기대값(PHASE별), 실제값, curl 종료 코드를 Markdown 표로 출력하고, 마지막에 PASS/FAIL 개수.
그다음 scripts/local-rehearsal.sh를 만들어서, openssl s_server 두 개(18443: 클라이언트 인증서 필수 + CRL 검사, 18444: 클라이언트 인증서 없음)를 띄우고
test-matrix.sh를 NLB_DNS=127.0.0.1로 돌려 줘. 실행해서 결과를 보여 줘.

    PHASE=base 기준으로 PASS 11 / FAIL 0이 나오면 됩니다.

    Warning

    "HTTP 200이 아니면 REJECT"로만 판정하면 위험합니다. 인증서 파일 경로가 틀리거나 NLB DNS가 잘못돼도 "거부됨 = 기대대로"가 되어 PASS로 보입니다. 테스트가 성립하지 않은 경우를 ERROR로 따로 세는지 확인하세요. 확인 방법: 아무것도 듣지 않는 포트로 NLB_DNS=127.0.0.1 CERTS=~/ws-lab/certs MTLS_PORT=18999 PLAIN_PORT=18998 bash scripts/test-matrix.sh를 실행하면 모든 행이 ERROR여야 합니다.

    Warning

    로컬 리허설은 신뢰 체인·CRL·EKU·만료만 흉내 냅니다. identity filter와 access log 사유 코드는 NLB에서만 확인할 수 있습니다. 리허설이 통과해도 Lab 3은 필요합니다.

    3단계. CloudFormation 템플릿 만들기¶

    Claude Code에 입력:

    test-plan.md의 테스트 환경을 infra/nlb-mtls.yaml CloudFormation 템플릿으로 만들어 줘.

- VPC 10.20.0.0/16, AZ 2개. public 10.20.0.0/24, 10.20.1.0/24 (IGW, NAT GW 1개), private 10.20.10.0/24, 10.20.11.0/24
- internal NLB(보안 그룹 사용), access log를 스택이 만드는 로그 버킷에 (NLB용 버킷 정책은 문서대로)
- AWS::ElasticLoadBalancingV2::TrustStore (CA 번들) + TrustStoreRevocation (CRL). 파일은 파라미터로 받은 기존 artifact 버킷에 있음
- TLS 443: mTLS verify + trust store / TLS 8443: mTLS off. 둘 다 같은 TCP 8080 대상 그룹, SslPolicy ELBSecurityPolicy-TLS13-1-2-2021-06
- 서버 인증서 ARN은 파라미터
- EC2 3대(AL2023 arm64, t4g.micro, IMDSv2): 대상 2대는 8080 HTTP이고 SSM 권한만 줘.
  클라이언트 1대는 역할을 따로 만들어 artifact 버킷 clients/만 읽게 하고(GetObject + prefix 조건 ListBucket),
  부팅 시 /opt/lab/certs에 받아 키는 600으로. 다운로드 실패가 숨겨지지 않게 cfn-signal + CreationPolicy로 알려.
  마지막에 /etc/profile.d/lab.sh를 만들어 NLB_DNS(NLB DNS 이름), SERVER_NAME=mtls.lab.internal, CERTS=/opt/lab/certs를 export해 (Lab 3 스크립트가 읽음). 성공 신호는 이 파일까지 쓴 다음에 보내.
- SG: 클라이언트 → NLB 443/8443, NLB → 대상 8080만
- 모든 리소스 태그 Project=ws-ai-nssa
- 속성 이름은 research.md와 CloudFormation 문서로 확인한 것만 써. identity filter는 템플릿에 넣지 마(Lab 3에서 CLI로).
다 쓰면 cfn-lint를 돌리고 오류가 없을 때까지 고쳐 줘.

    검증 체크포인트 2 — AI 환각 잡기¶

    cfn-lint가 통과해도 끝이 아닙니다. 이번 기능에서 실제로 일어나는 두 가지 함정을 직접 겪어 봅니다.

    함정 A: lint는 통과하지만 배포에서 실패하는 값

    Claude Code에 입력:

    실험이야. infra/nlb-mtls.yaml을 복사해서 /tmp/trap-a.yaml을 만들고, 8443 리스너에 MutualAuthentication Mode: passthrough를 넣은 뒤 cfn-lint를 돌려 줘.
그리고 research.md와 API 레퍼런스(MutualAuthenticationAttributes) 기준으로 이 값이 NLB에서 유효한지 판단해 줘. 원본 템플릿은 건드리지 마.

    cfn-lint는 통과합니다. CloudFormation 레퍼런스의 Mode 설명이 ALB·NLB를 구분하지 않고 off | passthrough | verify를 나열하기 때문입니다. 하지만 API 레퍼런스는 NLB에 off, verify만 허용합니다. 이 값은 배포할 때 API에서 실패합니다. 리허설에서 같은 값을 CLI로 보내 보니 이렇게 거부되었습니다.

    An error occurred (ValidationError) when calling the ModifyListener operation: Mutual Authentication mode passthrough is not supported on load balancers of type 'network'

    함정 B: 문서에는 있지만 lint가 거부하는 속성

    Claude Code에 입력:

    실험 2야. /tmp/trap-b.yaml에서 443 리스너의 MutualAuthentication에 ClientCertificateIdentityFilters(subject-ou exact Production)를 넣고 cfn-lint를 돌려 줘.
결과를 research.md의 "문서 불일치" 내용과 비교해서 설명해 줘.

    작성 시점 기준 cfn-lint는 E3002 Additional properties are not allowed ('ClientCertificateIdentityFilters' was unexpected)를 냅니다. 사용자 가이드에는 예시가 있지만 CloudFormation 스키마에는 아직 없습니다. 리허설(2026-11-26)에서 계정의 레지스트리 스키마(aws cloudformation describe-type --type RESOURCE --type-name AWS::ElasticLoadBalancingV2::Listener)를 보니 MutualAuthentication 속성은 IgnoreClientCertificateExpiry, Mode, TrustStoreArn, AdvertiseTrustStoreCaNames 넷뿐이었습니다. lint 스키마가 늦은 것이 아니라 CloudFormation 자체에 아직 없습니다.

    상황 lint 배포 어떻게 잡는가
    A. 스키마는 허용하지만 서비스가 거부(passthrough) 통과 실패 API 레퍼런스 대조, change set
    B. 문서에는 있지만 스키마에 없음(필터) 실패 change set은 만들어짐, 실행 결과는 미확인 문서끼리 대조, 레지스트리 스키마 확인, 우회 경로(CLI) 선택
    C. 아예 지어낸 속성(예: PassthroughHeaderName) 실패 실패 lint
    • 원본 infra/nlb-mtls.yaml은 cfn-lint 오류 0개다.
    • 템플릿의 mTLS 관련 속성(Mode, TrustStoreArn, IgnoreClientCertificateExpiry, CaCertificatesBundleS3Bucket/Key, RevocationContents)마다 근거 문서 URL을 말할 수 있다.
    • 로그 버킷 정책의 principal이 delivery.logs.amazonaws.com이다(NLB access log 문서 기준).
    • 대상 SG는 NLB SG에서 오는 8080만 허용한다.
    • 백엔드와 클라이언트의 IAM 역할이 분리되어 있고, 클라이언트 개인 키(clients/)는 클라이언트 역할만 읽을 수 있다.
    • 클라이언트 user data에 || true처럼 실패를 삼키는 코드가 없다.

    Info

    Claude에게 "이 템플릿에서 문서로 확인하지 않은 속성이나 값을 모두 나열해 줘"라고 물어보세요. 스스로 쓴 코드의 근거를 되묻는 질문은 가장 싸고 효과가 큰 검증입니다.

    4단계. 배포¶

    Claude Code에 입력:

    scripts/deploy.sh를 만들어 줘.
1) artifact 버킷 ws-ai-nssa-mtls-<계정>-<리전>을 만들고(퍼블릭 차단, 태그) truststore/ca-bundle.pem, truststore/crl.pem, clients/(클라이언트 인증서·키·lab-root-ca.pem)를 올려
2) 서버 인증서를 ACM에 import (ARN은 ~/ws-lab/.lab-state에 저장해서 두 번 import하지 않게)
3) aws cloudformation deploy로 스택 ws-ai-nssa-nlb-mtls 배포 (CAPABILITY_IAM, 태그 Project=ws-ai-nssa)
4) 출력값 표 보여 주기
모든 aws 명령에 --region "${LAB_REGION:-ap-northeast-2}"를 붙여. 공통 값은 scripts/lib.sh로 빼.
실행하기 전에 만들어질 리소스와 시간당 비용을 먼저 알려 줘.

    Claude가 비용을 알려 주고 실행 허가를 요청하면 확인한 뒤 승인합니다. 배포는 5분 안팎 걸립니다(리허설: 스택 생성 4분 11초, 그중 클라이언트 cfn-signal까지 52초).

    Warning

    참석자 환경에는 Bedrock용 AWS_REGION=us-east-1이 설정되어 있습니다. --region을 빠뜨리면 리소스가 us-east-1에 만들어집니다. starter kit의 hook이 리전 없는 aws 명령을 막지만, 스크립트 안의 명령은 hook이 보지 못합니다. 스크립트는 직접 읽어서 확인하세요.

    검증 체크포인트 3 — 배포된 것이 계획과 같은가¶

    Claude Code에 입력:

    배포된 리소스를 읽기 전용 명령으로만 확인해 줘.
- 443/8443 리스너의 Protocol, Port, SslPolicy, MutualAuthentication
- trust store 상태와 NumberOfCaCertificates, revocation 개수
- 대상 그룹 target health
- 로드 밸런서 속성 중 access_logs.*
결과를 test-plan.md의 환경 절과 비교해서 다른 점만 알려 줘.

    직접 확인할 명령 예:

    R="${LAB_REGION:-ap-northeast-2}"
L=$(aws cloudformation describe-stacks --region "$R" --stack-name ws-ai-nssa-nlb-mtls \
  --query "Stacks[0].Outputs[?OutputKey=='MtlsListenerArn'].OutputValue" --output text)
aws elbv2 describe-listeners --region "$R" --listener-arns "$L" --query 'Listeners[0].MutualAuthentication'
    • 443은 "Mode": "verify", 8443은 MutualAuthentication이 없거나 "Mode": "off".
    • trust store Status가 ACTIVE, CA 1개, revocation 1개.
    • 대상 2개 모두 healthy.
    • 템플릿의 클라이언트 user data가 /etc/profile.d/lab.sh(NLB_DNS, SERVER_NAME, CERTS)를 쓰고 그다음에 성공 신호를 보낸다. Lab 3의 모든 원격 명령이 이 파일을 읽습니다.

    리허설 결과: 443은 Mode: verify, IgnoreClientCertificateExpiry: false, AdvertiseTrustStoreCaNames: off, TrustStoreAssociationStatus: active, ClientCertificateIdentityFilters: []였고, 8443은 {"Mode": "off"}였습니다. trust store는 ACTIVE, CA 1개, revocation 1개(1건)였습니다. 대상 하나는 스택 완료 직후 initial이었다가 30초 안에 healthy가 되었습니다.
