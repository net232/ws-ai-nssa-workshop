    1-3. 설정과 권한¶

    목표¶

    • settings.json의 계층과 우선순위를 이해합니다.
    • 조회는 바로, 변경은 확인 후, 위험한 것은 금지하는 권한 규칙을 만듭니다.

    1. settings.json 계층¶

    파일 범위 git 공유
    ~/.claude/settings.json 나의 모든 프로젝트 아니오
    .claude/settings.json 이 프로젝트, 팀 공통 예
    .claude/settings.local.json 이 프로젝트, 나만 아니오 (.gitignore)

    같은 설정이 여러 곳에 있으면 좁은 범위가 이깁니다(local > project > user). 조직 관리 정책과 명령줄 옵션(--settings, --permission-mode 등)은 이 파일들보다 우선합니다. 권한 규칙은 파일끼리 합쳐지며, 같은 동작에 여러 규칙이 걸리면 deny → ask → allow 순서로 판단합니다.

    현재 적용된 규칙은 세션에서 /permissions로 확인합니다.

    2. 권한 규칙¶

    starter kit의 .claude/settings.json:

    {
  "permissions": {
    "allow": [
      "Bash(aws * describe-*)",
      "Bash(aws * list-*)",
      "Bash(aws sts get-caller-identity*)",
      "Bash(aws cloudformation validate-template *)",
      "Bash(cfn-lint *)",
      "Bash(openssl *)"
    ],
    "ask": [
      "Bash(curl *)",
      "Bash(aws * delete-*)",
      "Bash(aws * terminate-*)",
      "Bash(aws cloudformation deploy *)",
      "Bash(aws * modify-*)"
    ],
    "deny": [
      "Read(~/.aws/credentials)",
      "Read(./**/*.key)",
      "Bash(aws * --profile prod*)",
      "Bash(aws iam create-access-key*)"
    ]
  }
}
    구분 의도 예
    allow 읽기 전용 조회와 로컬 검증은 묻지 않고 실행 → 조사 속도 describe-*, list-*, cfn-lint
    ask AWS에 변경을 가하는 명령은 매번 사람이 확인 deploy, delete-*, modify-*
    deny 실습에서 절대 필요 없는 것 자격 증명 파일 읽기, 프로덕션 프로필, 액세스 키 발급

    와일드카드는 생각보다 넓습니다

    규칙의 *는 접두어만이 아니라 아무 문자열과 일치하고, 명령 전체 텍스트를 대상으로 비교합니다. 그래서 Bash(aws * describe-*)는 모든 서비스의 describe-*를 허용합니다. 실습 계정에서는 편리하지만, 업무 계정에서는 Bash(aws ec2 describe-*)나 Bash(aws elbv2 describe-*)처럼 서비스를 적어 범위를 좁히세요. 서브커맨드 앞에 *를 둔 규칙에는 Claude Code가 시작할 때 경고를 표시할 수 있습니다. Read(...)의 경로 패턴은 gitignore 형식을 따릅니다. 자세한 문법은 권한 문서를 확인하세요.

    Read 금지는 Bash를 막지 않습니다

    Read(~/.aws/credentials)를 deny에 넣어도, Bash로 cat ~/.aws/credentials를 실행하거나 curl -d @파일로 파일을 보내는 것은 Read 규칙과 별개입니다. 그래서 외부로 데이터를 보낼 수 있는 curl은 allow가 아니라 ask에 둡니다. 자격 증명은 파일로 두지 말고 인스턴스 역할이나 SSO를 쓰는 것이 가장 확실합니다.

    • 규칙 형식은 도구(패턴)입니다. *는 임의의 문자열과 맞습니다. Read(...), Edit(...)에는 파일 경로 패턴을 씁니다.
    • 승인 창에서 "다시 묻지 않기"를 고르면 .claude/settings.local.json에 allow 규칙이 추가됩니다. 가끔 열어 보고 너무 넓은 규칙은 지웁니다.

    Warning

    패턴 규칙은 명령 문자열을 기준으로 합니다. aws ... describe-*를 허용해도 get-*처럼 비밀 값을 읽는 조회(예: secretsmanager get-secret-value)는 따로 판단해야 합니다. 그래서 get-* 전체를 allow에 넣지 않았습니다.

    3. 환경 변수¶

    Claude Code에만 줄 환경 변수는 settings.json의 env에 둘 수 있습니다.

    {
  "env": {
    "CLAUDE_CODE_USE_BEDROCK": "1",
    "AWS_REGION": "us-east-1"
  }
}

    워크숍 IDE는 이 값을 /etc/profile.d에 이미 설정했으므로 따로 넣지 않아도 됩니다. 어느 쪽이든 Claude Code가 실행하는 aws CLI에도 같은 값이 상속된다는 점(1-1의 리전 함정)은 같습니다.

    4. 안전 수칙¶

    반드시 지킵니다

    • 실습 전용 계정에서만 사용합니다. 고객 계정, 프로덕션 계정의 자격 증명이 있는 셸에서 Claude Code로 변경 작업을 하지 않습니다.
    • 액세스 키를 파일·프롬프트·CLAUDE.md에 붙여 넣지 않습니다. 인스턴스 역할이나 SSO 임시 자격 증명을 씁니다.
    • --dangerously-skip-permissions(bypassPermissions)를 쓰지 않습니다.
    • 고객 정보(계정 ID, 이름, IP 계획)를 프롬프트에 넣을 때는 회사의 데이터 처리 지침을 따릅니다.
    • AI가 만든 IAM 정책·보안 그룹은 0.0.0.0/0, "Action": "*"가 있는지 직접 확인합니다.

    미니 실습 (3분)¶

    Claude Code에 입력:

    다음 세 명령을 차례로 실행해 줘: (1) ap-northeast-2의 VPC 목록 조회 (2) 존재하지 않는 스택 ws-ai-dummy 삭제 (3) ~/.aws/credentials 읽기

    검증 체크포인트

    • (1)은 묻지 않고 실행됩니다(allow).
    • (2)는 리전이 없으면 먼저 1-4의 hook이 막고, Claude가 --region을 붙여 다시 시도하면 승인 창이 뜹니다(ask). 거절합니다.
    • (3)은 거부됩니다(deny). Claude가 다른 방법으로 우회하려 하지 않는지도 봅니다.
