    1-5. 실전 팁¶

    1. 좋은 프롬프트, 나쁜 프롬프트¶

    나쁜 프롬프트 문제 좋은 프롬프트
    "NLB mTLS 테스트 환경 만들어 줘" 범위·기준이 없어 AI가 마음대로 정함 "plan mode로. NLB mTLS verify 모드를 검증할 환경을 계획해 줘. VPC 1개, 클라이언트 EC2 1대, 대상 EC2 2대. 시간당 비용과 삭제 방법 포함"
    "이거 왜 안 돼?" 증상·관찰 정보가 없음 "curl --cert 결과가 alert unknown ca야. 출력 붙임. 가설 3개와 각각 확인할 명령을 먼저 제시하고, 실행은 내가 고른 것만 해"
    "CloudFormation 템플릿 써 줘" 검증 기준 없음 "템플릿을 쓰고 cfn-lint 통과까지 반복해. 신규 속성은 CFN 문서 URL을 주석으로 달아"
    "Cloud WAN 워크숍 만들어 줘" 한 번에 너무 큼 "Cloud WAN 마이그레이션 워크숍의 스토리보드만 먼저. 모듈 5개, 모듈마다 학습 목표와 실습 결과물 한 줄"
    "이 정도면 맞지?" 동의를 유도함 "이 템플릿에서 틀렸을 가능성이 높은 곳 3군데를 근거와 함께 찾아 줘"

    2. 일하는 방식¶

    • 작게 쪼갭니다. 조사 → 계획 → 템플릿 → 배포 → 테스트를 한 번에 시키지 않고 단계마다 결과를 확인합니다. Lab 1–6이 이 순서입니다.
    • 먼저 plan mode. 변경이 있는 작업은 계획을 보고 승인한 뒤 실행합니다. 계획 단계에서 고치는 비용이 가장 쌉니다.
    • 출처를 요구합니다. "문서 URL을 함께", "확인한 사실과 추측을 나눠서". 신규 기능일수록 중요합니다.
    • 모르면 모른다고 하게 합니다. "확인하지 못한 것은 TODO(확인 필요)로 남겨" 같은 규칙을 AGENTS.md에 둡니다.
    • 검증 기준을 프롬프트에 넣습니다. "cfn-lint 통과", "curl 응답 코드가 200", "Reachability Analyzer 결과가 reachable"처럼 기계가 판단할 수 있는 완료 조건을 주면 Claude가 스스로 반복해 맞춥니다.
    • 증적을 남기게 합니다. "성공했다"는 보고 대신 명령과 출력을 results/에 저장하게 합니다. 워크숍 페이지를 쓸 때 그대로 재료가 됩니다.

    3. 컨텍스트 관리¶

    • 긴 로그·큰 JSON은 통째로 붙이지 말고 파일로 저장한 뒤 @파일로 참조하거나 "필요한 필드만 jq로 뽑아서 봐"라고 합니다.
    • 주제가 바뀌면 /clear, 같은 주제를 길게 이어 가면 /compact <남길 것>.
    • /context로 무엇이 컨텍스트를 차지하는지 봅니다. MCP 도구가 많으면 쓰지 않는 서버는 끕니다.
    • 넓은 조사(문서 여러 개 읽기, 많은 파일 훑기)는 subagent에 맡기고 결론만 받습니다.

    4. 병렬로 일하기¶

    • 터미널을 두 개 열고 서로 다른 일을 시킬 수 있습니다. 예) 한쪽은 Track A 테스트, 다른 쪽은 워크숍 페이지 초안.
    • 같은 저장소에서 파일이 겹치면 claude -w <이름>(git worktree)으로 작업 폴더를 분리합니다.
    • AWS 리소스는 worktree와 상관없이 같은 계정에 만들어집니다. 스택 이름이 겹치지 않게 접두어를 다르게 줍니다.

    5. 비용¶

    • 세션 비용은 /cost로 봅니다. Bedrock 요금은 AWS 청구서에도 나타납니다.
    • 같은 질문을 반복하는 것보다 규칙을 AGENTS.md에, 절차를 skill에 두는 것이 토큰을 아낍니다.
    • AWS 리소스 비용이 더 큽니다. 실습이 끝날 때마다 삭제를 확인합니다(정리 페이지).

    6. 실패 사례와 대처¶

    흔한 환각: 그럴듯한 속성과 파라미터

    모델은 학습 시점 이후의 기능을 모르거나, 있을 법한 이름을 지어내기도 합니다. 예를 들어 새 기능을 설정할 때

    • CloudFormation에 없는 속성 이름을 쓰거나 다른 리소스(ALB)의 속성을 NLB에 그대로 가져옵니다.
    • CLI 옵션 이름은 맞지만 허용 값(enum)을 잘못 씁니다.
    • 지원하지 않는 리전이나 리스너 프로토콜 조합을 가능하다고 말합니다.

    대처:

    단계 방법
    쓰기 전 "AWS 문서(aws-knowledge)에서 이 리소스의 속성 목록을 먼저 확인하고 써"
    쓴 뒤 cfn-lint(스키마 검사), aws cloudformation validate-template, CLI는 aws <svc> <cmd> help로 옵션 확인
    배포 시 실패 이벤트를 그대로 붙이고 "추측 말고 이벤트와 문서로 원인을 찾아" (aws-iac MCP의 배포 실패 진단)
    리뷰 작성한 세션이 아닌 독립 리뷰어(subagent, Codex)에게 대상과 관점만 넘김

    Info

    cfn-lint는 리소스 스키마가 최신이어야 새 속성을 압니다. 신규 기능을 다룰 때는 cfn-lint --update-specs 또는 최신 버전 설치 후 검사합니다. 반대로, lint가 모르는 속성이라고 해서 곧 환각이라고 단정하지 말고 문서로 확인합니다.
