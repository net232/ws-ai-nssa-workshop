    Lab 6. Review & Package¶

    목표¶

    • 작성자와 분리된 독립 리뷰어에게 Lab 1–4의 산출물을 리뷰받고, 지적 사항을 직접 검증합니다.
    • Lab 1–4에서 한 일을 skill로 만들어 다음 신규 기능 테스트에 다시 씁니다.

    라이프사이클 위치: 7 Review, 8 Package

    왜 독립 리뷰인가¶

    같은 세션의 Claude에게 "방금 만든 것 리뷰해 줘"라고 하면, Claude는 자기가 왜 그렇게 만들었는지 이미 알고 있습니다. 그래서 같은 가정을 되풀이하기 쉽습니다. 사람 리뷰도 마찬가지입니다. 작성자가 "여기는 이래서 괜찮아"라고 먼저 설명하면 리뷰어는 그 설명을 따라갑니다.

    독립 리뷰의 규칙은 두 가지입니다.

    1. 리뷰어에게는 리뷰 대상(파일 경로, diff)과 리뷰 관점만 넘깁니다. 작성자의 판단이나 가설은 넘기지 않습니다.
    2. 리뷰어의 지적을 그대로 받아들이지 않습니다. 실제 코드와 문서에 대조해 확인된 것, 불확실한 것, 틀린 것으로 나눕니다.
    리뷰어 독립성 언제 쓰나
    같은 세션의 Claude 낮음: 작성 맥락을 공유함 오탈자, 빠진 파일 확인
    subagent (net-reviewer) 중간: 별도 컨텍스트, 같은 모델 일반 리뷰. 이 Lab의 기본
    다른 모델 (Codex CLI 등) 높음: 다른 모델, 다른 편향 보안, IaC, 핵심 로직
    동료 SA 가장 높음 고객에게 나가기 전

    1. subagent로 리뷰하기¶

    Starter kit의 .claude/agents/net-reviewer.md를 열어 봅니다. 읽기 전용 도구만 쓰고, 작성자의 설명을 받지 않으며, 지적 사항마다 근거(파일:줄, 문서 URL)를 붙이도록 정의되어 있습니다.

    cd ~/ws-lab
cat .claude/agents/net-reviewer.md
claude

    리뷰할 트랙을 고릅니다. 시간이 있으면 두 트랙을 모두 리뷰합니다.

    Claude Code에 입력:

    net-reviewer 에이전트로 다음 파일을 리뷰해 줘. 내 의견이나 네가 만든 이유는 넘기지 말고, 파일 경로와 관점만 전달해.
- 대상: infra/nlb-mtls.yaml, scripts/gen-certs.sh, scripts/test-matrix.sh, results.md
- 관점: (1) AWS 문서와 다른 CloudFormation 속성이나 CLI 옵션, (2) 보안(보안 그룹 범위, 개인 키 처리, IAM 권한), (3) 테스트 매트릭스의 빈틈(빠진 실패 경로, 증적 없는 판정), (4) 정리 누락
리뷰 결과는 review.md로 저장해 줘.

    cd ~/ws-cloudwan-workshop && claude

    Claude Code에 입력:

    net-reviewer 에이전트로 다음 파일을 리뷰해 줘. 내 의견이나 네가 만든 이유는 넘기지 말고, 파일 경로와 관점만 전달해.
- 대상: policy/core-network-policy.json, scripts/check_policy.py, content/ 아래 모듈 페이지, static/images/ 구성도의 레이아웃 스펙
- 관점: (1) Cloud WAN 정책 키와 CloudFormation 속성이 AWS 문서와 다른 곳, (2) 페이지의 명령·값이 템플릿·스크립트와 맞지 않는 곳, (3) 구성도가 실제 토폴로지(segment, attachment, peering)와 다른 곳, (4) 참석자가 막힐 만한 빠진 설명
리뷰 결과는 review.md로 저장해 줘.

    확인할 점

    Ctrl+O로 트랜스크립트 뷰어를 열고, Claude가 subagent를 호출한 도구 입력(프롬프트)을 확인합니다. "이 부분은 의도적으로 이렇게 했다" 같은 작성자 설명이 들어가 있으면 독립 리뷰가 아닙니다. 그럴 때는 Claude에게 다시 요청합니다.

    2. 지적 사항 검증하기¶

    Claude Code에 입력:

    review.md의 지적 사항을 하나씩 실제 파일과 AWS 문서에 대조해서 검증해 줘. 각 항목을 "확인됨 / 불확실 / 오탐"으로 분류하고 근거를 붙여. 확인된 항목만 수정 계획을 세우고, 수정은 내가 승인한 뒤에 해.

    검증 체크포인트¶

    • 각 지적 사항에 근거가 붙어 있는가? 근거는 파일과 줄 번호, 또는 문서 URL이어야 합니다.
    • "오탐"으로 분류한 항목이 있다면, 그 이유를 직접 읽고 납득할 수 있는가?
    • 수정한 뒤 cfn-lint와 해당 테스트 케이스를 다시 실행했는가?

    3. (선택) 다른 모델로 교차 리뷰¶

    Codex CLI가 설치된 환경이라면 다른 모델로 같은 대상을 리뷰합니다. 읽기 전용 샌드박스(-s read-only)로 실행하므로 파일을 고치지 않습니다. 리뷰 깊이는 대상에 맞게 model_reasoning_effort로 정합니다.

    수준 예 effort
    가벼움 오탈자, 문구, 작은 설정 low
    일반 기능 변경, 리팩터링, 문서 구조 medium
    심층 보안, IaC, 핵심 로직 high 
    codex exec -s read-only --ephemeral -c model_reasoning_effort="high" \
  -o review-codex.md \
  "infra/nlb-mtls.yaml 과 scripts/*.sh 를 리뷰해. 관점: AWS 문서와 다른 속성, 보안, 테스트 빈틈, 정리 누락. 지적마다 파일:줄 근거를 붙여."

    두 리뷰를 비교해 봅니다. 한쪽에만 나온 지적이 가장 가치 있는 경우가 많습니다.

    Matt Pocock skills로 리뷰하기 (1-6 참고)

    작업 폴더가 git 저장소이고 커밋이 쌓여 있다면 /mattpocock-skills:code-review를 쓸 수 있습니다. 이 skill은 기준점 이후 변경을 두 subagent가 병렬로 리뷰합니다. 한 subagent는 AGENTS.md의 규칙을 지켰는지(Standards)를, 다른 subagent는 test-plan.md의 요구 사항을 만족하는지(Spec)를 봅니다.

    /mattpocock-skills:code-review 첫 커밋 이후 변경을 리뷰해 줘. Spec은 test-plan.md야.

    Success

    이 규칙(리뷰는 독립적으로, 지적은 검증해서)을 사용자 ~/.claude/CLAUDE.md에 적어 두면 모든 프로젝트에서 Claude가 따릅니다.

    4. skill로 자산화하기¶

    Lab 1–4에서는 조사, 계획, 구축, 검증, 디버깅을 프롬프트로 하나씩 지시했습니다. 다음 신규 기능이 나와도 같은 순서를 밟습니다. 이 절차를 skill로 만들어 둡니다.

    Claude Code에 입력:

    이 폴더의 산출물(research.md, test-plan.md, infra/, scripts/, results.md, rca.md, review.md)을 보고, 다른 신규 네트워킹 기능에도 쓸 수 있는 skill을 만들어 줘.
- 위치: .claude/skills/net-feature-test/SKILL.md
- 사용자가 /net-feature-test <기능 이름>으로만 호출하게 해 줘(자동 호출 안 함).
- 단계마다 산출물 파일을 남기고, 검증 결과를 보고하고, 내 승인을 받은 뒤 다음 단계로 가게 해 줘.
- NLB mTLS에만 해당하는 내용은 빼고 일반화해 줘.
먼저 plan mode로 구조를 보여 줘.

    만든 skill을 이 Lab의 참고 답안과 비교합니다.

    정답 참고: ~/ws-solutions/skills/net-feature-test/SKILL.md 

    ---
name: net-feature-test
description: AWS 신규 네트워킹 기능을 조사하고 테스트 계획, IaC, 테스트 스크립트, 결과 보고서까지 라이프사이클 순서로 진행한다. ...
argument-hint: "<기능 이름 또는 What's New URL>"
disable-model-invocation: true
---

대상 기능: $ARGUMENTS

아래 단계를 순서대로 진행한다. 각 단계가 끝나면 산출물 파일을 저장하고,
검증 결과를 보고한 뒤 사용자의 승인을 받고 다음 단계로 넘어간다.

## 1. Discover → research.md   (모든 사실에 출처 URL, 미확인은 "미확인")
## 2. Plan → test-plan.md      (케이스마다 입력·기대 결과·판정 방법)
## 3. Build → infra/, scripts/  (cfn-lint, bash -n, --region "$LAB_REGION", 태그)
## 4. Verify → results.md      (기대/실제/판정/증적 표)
## 5. Troubleshoot → rca.md    (가설 → 확인 명령 → 결과 → 결론)
## 6. Cleanup → cleanup.sh     (삭제는 승인 후, 잔여 태그 리소스 확인)
    전체 파일은 ~/ws-solutions/skills/net-feature-test/SKILL.md에 있습니다.

    skill 시험해 보기¶

    새 세션에서 다른 기능으로 1단계만 실행해 봅니다. What's New의 Networking & Content Delivery 항목 중 최근 기능 하나를 고릅니다.

    claude

    Claude Code에 입력:

    /net-feature-test <고른 기능 이름>

    1단계(Discover)가 끝나고 승인을 기다리면 성공입니다. research.md의 출처 URL을 몇 개 직접 열어 봅니다. 확인이 끝나면 Esc로 멈춥니다. 이 기능의 테스트는 워크숍 후 과제입니다.

    검증 체크포인트¶

    • /net-feature-test가 자동완성 목록에 보이는가?
    • skill이 단계마다 멈추고 승인을 기다리는가?
    • skill 본문에 NLB mTLS에만 해당하는 내용(포트 443, trust store 등)이 남아 있지 않은가?

    skill 다듬기¶

    • skill 본문을 쓰기 전에 writing-for-agents 원칙을 적용해 달라고 요청하면, description의 트리거 문구와 단계별 완료 조건이 좋아집니다(1-6 참고).
    • 세션을 마치기 전에 /retro를 실행하면, 오늘 겪은 문제를 바탕으로 AGENTS.md 규칙, hook, skill에서 무엇을 고칠지 제안받습니다.
    • 작업을 다음 날 이어 가려면 /handoff 내일은 Lab 5 결과물 리뷰처럼 실행해 인수인계 문서를 남깁니다.

    5. 팀과 공유하기¶

    범위 위치 공유 방법

    이 저장소 <repo>/.claude/skills/ git으로 커밋
    팀 전체 plugin 팀 plugin marketplace

    강사가 이 워크숍을 만들 때 쓴 구성도 skill(skill-aws-arch-diagram)과 번역 skill(skill-aws-ko-translation)도 이런 식으로 만들어 공유한 것입니다.

    정리¶

    • 리뷰어에게는 대상과 관점만 넘기고, 지적은 직접 검증합니다.
    • 리뷰가 중요할수록 다른 컨텍스트, 다른 모델, 다른 사람으로 독립성을 높입니다.
    • 두 번 이상 하는 일은 skill로 만들어 사람의 판단 지점(승인)을 절차 안에 넣어 둡니다.
